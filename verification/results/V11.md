- 状态：PASS

- API Key：通过环境变量 `OPENROUTER_API_KEY` 提供，未写入任何文件或命令行

### 执行的命令

```bash
python3 examples/rag_eval/run_eval.py                                  # 检查点 1
NANOCODE_API_KEY="$OPENROUTER_API_KEY" python3 examples/rag_eval/run_eval.py \
    --embed-provider "" --embed-base-url https://openrouter.ai/api/v1 \
    --embed-model qwen/qwen3-embedding-8b --verbose                    # 检查点 2、3
```

注意：第二条命令必须让 Key 通过 `NANOCODE_API_KEY` 传入。评测脚本没有 `--embed-api-key` 参数，
用 `--embed-provider` 时 Key 由预设的环境变量决定；OpenRouter 不在预设里，所以只能走通用的回退变量。
第一次尝试没有带 Key，返回 `HTTP 401: No cookie auth credentials found`，脚本如实打印了"向量化失败"并跳过向量行，
没有静默给出错误结果。

### 结果（语料 32 篇文档、220 个块，22 道题）

| 方法 | recall@1 | recall@3 | recall@5 | MRR |
|---|---|---|---|---|
| grep-原句 | 0% | 0% | 0% | 0.00 |
| grep-关键词 | 0% | 23% | 41% | 0.20 |
| bm25 | 36% | 91% | 95% | 0.62 |
| vector（qwen3-embedding-8b） | 77% | 86% | 100% | 0.84 |
| hybrid（RRF 融合） | 73% | 95% | 95% | 0.84 |

### 怎么解读

- **向量检索明显提升了第 1 名的准确率**：recall@1 从 BM25 的 36% 提升到 77%，MRR 从 0.62 提升到 0.84。说明题目是转述、不是原文用词时，语义匹配比关键词强得多。
- **混合检索在 recall@3 上最好（95%）**，但 recall@1 反而比纯向量低（73% vs 77%）。RRF 融合在这 22 道题上没有比纯向量更好，只在前 3 名的覆盖上略胜。
- **样本很小**：22 道题，差 1 题就是 4–5 个百分点。这些数字只能说明"在这个语料和这批题上，向量明显优于 BM25"，不能推广成通用结论。
- **和旧记录不可直接比较**：之前的基线（bm25 R@3 91%）是 11 篇文档、102 个块上测的；现在语料已扩大到 32 篇、220 个块，所以基线数字不一定相同。两次记录各自只和自己的语料对应。

### 发现的问题

- 评测脚本的 `--embed-provider` 只能选预设厂商，没有直接指定 Key 的参数，接入 OpenRouter 这类通用中转时要靠 `NANOCODE_API_KEY` 回退。
  建议以后给脚本加 `--embed-api-key-env` 参数，免得依赖隐式回退。
- 旧版文档写"OpenRouter 目前不一定提供 embedding 接口"已经过时：OpenRouter 现在提供 33 个 embedding 模型，接口与 OpenAI 兼容。
