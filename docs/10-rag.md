# 10 · RAG：按含义检索文档

> 对应源码：`nanocode/rag.py`、`nanocode/tools/rag_tool.py`、`examples/rag_eval/`

## 先问一个问题：为什么编程 Agent 默认不用 RAG？

Claude Code 这类编程 Agent 找代码，主要靠 `glob`、`grep`、`read_file` 现场搜索，而不是预先建向量索引。原因很实际：

- 代码里的标识符是精确的（`edit_file`、`PermissionManager`），grep 一搜就中。
- 代码天天在变，索引容易过期；grep 永远读的是磁盘上最新的文件。
- 搜不到可以换个关键词再搜，Agent 本来就能多轮尝试。

那为什么 nanocode 还加了 RAG？因为**文档和知识库的情况不一样**：用户用自然语言提问（"怎样避免大量搜索把主对话撑满"），文档里写的是"子 Agent 拥有独立上下文"。词对不上，grep 就找不到。企业里的客服知识库、产品手册、内部 wiki 都是这种场景。

所以 `search_docs` 和 `grep` 是分工，不是替代。工具说明里写明了这一点，模型才知道什么时候用哪个。

## 管线

```
文件 ─▶ chunk_file ─▶ tokenize ─▶ BM25 ─────────┐
         切块         分词        关键词排名       ├─▶ RRF 融合 ─▶ top-k
              └──────▶ Embedder ─▶ 余弦相似度 ───┘       （可选：向量）
```

### 1. 切块

块太大，检索不准，还浪费上下文；块太小，丢掉前后文。`chunk_file` 的做法：

- Markdown 遇到标题就开新块，并记住当前标题；代码块里的 `#` 不算标题。
- 超过 900 字符就在空行处再切；没有空行的超长段落硬切。
- 不做 overlap，因为边界落在标题和空行上，语义本来就完整。
- 标题会拼进被检索的文本里，标题往往概括了这一块讲什么。

块需要记录起止行号，这样模型拿到结果后可以用 `read_file` 的 offset/limit 精确读取原文，而不是只能看片段。

### 2. BM25 与中文分词

BM25 是经典的关键词打分：

```
score = Σ IDF(词) · tf·(k1+1) / (tf + k1·(1 - b + b·块长/平均块长))
```

- **tf**：词在块里出现的次数，出现越多越相关，但边际递减。
- **IDF**：词越稀有越重要。"的"每块都有，IDF 接近 0。
- **长度归一化**：避免长块仅因包含更多词就占便宜。

中文没有空格。常见做法是引入分词库，nanocode 用更简单的办法：**相邻两字（bigram）当作一个词**。"必须唯一" → `必须`、`须唯`、`唯一`。不需要任何依赖，对短查询效果不错，代价是索引变大、会产生一些无意义的词。查询和文档必须用同一个分词函数，否则对不上。

### 3. 向量检索（可选）

`Embedder` 调用任意 OpenAI 兼容的 `/embeddings` 接口，把每个块变成一个向量，查询时把问题也变成向量，按余弦相似度排序。它能匹配"意思相近但用词不同"的内容，这是 BM25 做不到的。

代价：需要 API 调用（有费用和延迟）、索引里要存向量、换了向量模型后旧向量全部作废（代码里会检测并重新计算）。

### 4. 混合检索与 RRF

BM25 的分数可能是 0 到 30，余弦相似度是 0 到 1，量纲不同，直接相加没有意义。**RRF（倒数排名融合）**只看名次：每个榜单里排第 r 名的得 `1/(60+r)` 分，各榜单相加。在两个榜单里都出现的块会排到前面，不用调权重。

### 5. 增量索引

`DocIndex.refresh()` 比较每个文件的 `mtime + size`：没变的复用旧块和旧向量，变了的重新切块，只给缺向量的块调用 embedding。索引存放在 `.nanocode/index/docs.json`。`search_docs` 每次调用前都会 refresh，没有变化时开销只是一次 stat。

## 文档从哪里来

RAG 的语料有两个来源，要分清楚：

| 场景 | 语料范围 | 由什么决定 |
|---|---|---|
| Agent 调用 `search_docs` | **Agent 的工作目录**（启动 nanocode 时所在的项目）下匹配的文件 | 默认 `**/*.md`、`**/*.markdown`、`**/*.txt`、`**/*.rst`；可用 `settings.json` 的 `rag.include` 改成别的范围 |
| 评测 `examples/rag_eval/` | 本项目（`--root` 指定，默认 nanocode 本身）的 `docs/*.md`，即 `docs/` 顶层的 17 个文件，不含子目录 | 脚本里的 `CORPUS_GLOB = "docs/*.md"`；grep 基线和 BM25、向量用的是同一份语料 |

几点要注意：

- **工具只索引工作目录，不索引 nanocode 自己的源码。** 在别人的项目里启动 nanocode，`search_docs` 查的是那个项目的 README 和文档。
- **索引缓存在工作目录的 `.nanocode/index/docs.json`**，目录里自带 `.gitignore`，不会被提交。文件的修改时间或大小变了才会重新切块、重新计算向量。
- **目录遍历会跳过 `.git` 等忽略目录。** 其余匹配的文件都会进入索引，包括你不想让模型读到的内容，所以大项目建议用 `rag.include` 收窄范围。
- **评测的语料是 nanocode 自己的 `docs/` 顶层文档，17 篇、221 个块**：01–13 章原理文档、学习路线、练习、以及 journey、resume、workflow 三篇流程文档。不包括 `docs/platform/` 下的平台设计文档。题目是 22 道用自然语言转述知识点的问题（见 `examples/rag_eval/questions.json`），所有标准答案都在这 17 个文件里。这意味着评测结果是在"本项目文档"上的结果，换成别的语料，排序可能不同。

## 使用

默认不需要任何配置，`search_docs` 会用 BM25 检索工作目录里的 `.md / .txt / .rst`。要启用向量和混合检索，在 `.nanocode/settings.json` 里加：

```json
{
  "rag": {
    "include": ["docs/**/*.md", "README.md"],
    "embedding": {"provider": "qwen", "model": "text-embedding-v3"}
  }
}
```

`provider` 可以是 `llm/__init__.py` 里的任一预设（会读取对应的 API Key 环境变量），也可以直接给 `base_url` 和 `api_key_env`。向量化失败（没网、Key 错误）时会自动退回 BM25，并在工具结果里提示原因，不会让 Agent 崩溃。

## 评测：不要凭感觉说 RAG 更好

`examples/rag_eval/` 用本项目的 `docs/` 作语料、22 道自然语言问题，比较几种找文档的办法：

```bash
python3 examples/rag_eval/run_eval.py --verbose
python3 examples/rag_eval/run_eval.py --embed-provider qwen --embed-model text-embedding-v3   # 加上向量和混合
```

指标按文件粒度：**recall@k**（前 k 个结果里有正确文档的问题占比）和 **MRR**（正确文档排名倒数的平均值）。

在本项目 `docs/` 顶层（17 篇文档、221 个块）上的运行结果，向量来自 OpenRouter 的 `qwen/qwen3-embedding-8b`（4096 维）：

| 方法 | recall@1 | recall@3 | recall@5 | MRR |
|---|---|---|---|---|
| grep-原句 | 0% | 0% | 0% | 0.00 |
| grep-关键词 | 0% | 32% | 55% | 0.25 |
| bm25 | 36% | 91% | 95% | 0.61 |
| vector | 77% | 91% | 100% | 0.84 |
| hybrid（RRF） | 73% | 95% | 95% | 0.84 |

更早的一次运行是在 11 篇文档、102 个块上测的（bm25 recall@3 91%，grep-关键词 73%）。语料变了，数字就不能直接比较，这也正是下面要强调的。另有一次运行的 grep 基线误用了包括 `docs/platform/` 在内的 32 个文件，而 BM25 和向量只索引 17 个，比较不公平，数字已作废；修正过程见 `verification/results/V11.md`。

方法说明：`grep-原句` 把整句问题当字符串去 grep；`grep-关键词` 把问题拆成关键词（和 BM25 同一套分词），任一词命中的行都算，按命中行数给文件排序；`bm25` 是分块后取每个文件得分最高的块。
注意：这些文档本身会被检索，所以每增加或修改一篇文档（包括这一章），数字都可能小幅变化。完整的运行记录见 `verification/results/V11.md`。

### 这组结果该怎么读

- **整句 grep 是 0%**，符合预期：自然语言问句不会原样出现在文档里。
- **BM25 并没有压倒"关键词 grep"**。在前 1 名上，关键词 grep 反而更好；BM25 的优势只体现在前 3 名，前 5 名打平。
- **语料一变，数字就变**：给 docs/04 补写安全章节之后，关键词 grep 的 recall@3 从 82% 掉到 73%，BM25 的 MRR 从 0.65 升到 0.67，而问题一道没改。小评测的波动就是这么大。这里的关键词 grep 是一个很宽容的基线（用了同样的 bigram 分词，任意词命中都算），现实中模型自己挑关键词，不一定这么好。
- **只有 22 道题**，一两道题的变化就会让百分比跳几个点，不能据此下结论。换语料、换题目，排序可能不同。
- **向量和混合检索没有跑**：开发环境连不上 embedding 服务。上面的命令需要你带 API Key 自己跑，不要想当然地认为混合一定更好。

从这个小实验能得到的真正结论是方法论：先定义"什么算找对"，建一个哪怕很小的评测集，然后用数字比较。改分词、改块大小、换 embedding 模型、加重排，都应该回来跑一遍这个脚本。

## 面试里怎么讲

- 为什么这个场景用 RAG，那个场景用 grep：看内容是精确标识符还是自然语言，看数据变化频率。
- 做了哪些取舍：块大小、中文怎么分词、为什么用 RRF 而不是加权求和、索引怎么增量更新。
- 怎么验证的：评测集怎么建、指标是什么、结果有什么局限。能讲清楚"我的评测很小，结论只是参考"，比报一个漂亮数字更可信。

## 还可以继续做的

- **重排（rerank）**：先用 BM25 加向量取前 30，再用交叉编码器或让大模型给前 30 打分重排。
- **查询改写**：让模型先把口语化的问题改写成几个检索查询。
- **按文件类型选择切块策略**：代码按函数切，表格单独处理。
- **引用与溯源**：回答时附上文件和行号，方便用户核对（`search_docs` 已经返回了行号）。
- **更大的评测集**：从真实使用日志里收集问题，覆盖更多失败类型。
