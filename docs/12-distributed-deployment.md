# 12 分布式部署：给 1000+ 用户使用还差什么

nanocode 现在是一个**单用户、单进程、单工作目录**的学习项目：一个 `nanocode --web` 进程只服务一个会话、一个人。
这一章回答一个问题：如果要把它部署到分布式环境，给 1000 名以上的用户同时使用，需要做哪些事、按什么顺序做。

先给结论：难点不在"多开几台机器"，而在三件事。

1. **执行隔离**：Agent 会在服务器上执行任意 bash 命令。多用户之后，这就是"让陌生人在你的机器上跑代码"。每个会话必须跑在独立的沙箱里，网络出口受控。这是上线的前提，不是优化项。
2. **身份与多租户**：现在整个服务只有一个令牌，没有"用户"的概念。需要登录、授权，并保证一个用户看不到、碰不到另一个用户的会话和文件。
3. **状态外置**：会话、事件、权限请求都在进程内存和本地 JSON 文件里。进程一挂或请求落到另一台机器，状态就丢了。

其余的（LLM 网关、限流计费、可观测性、发布流程）都围绕这三件事展开。

> 本章里的容量数字、工期都是**估算**，用来定量级和排优先级，上线前要用压测和真实用量替换。

> 本章只讨论"把现在的编程 Agent 部署给 1000 人用"。企业级平台、通用 Agent，以及千万、十亿用户规模的设计，见 [Agent 平台设计文档集](platform/README.md)。

## 一、现状盘点：哪些设计假设了"单用户单机"

下表每一行都对应到代码，是后面每一项改造的出发点。

| 位置 | 现在的做法 | 多用户分布式下的问题 |
|---|---|---|
| `web/server.py` `WebApp` | 一个 `WebApp` 绑定一个 `Session`；启动时生成**一个**令牌注入页面 | 没有用户身份：拿到页面的人都能驱动同一个 Agent。不能区分、隔离用户 |
| `web/server.py` `chat()` | 全局 `busy` 标志，一次只跑一个任务 | 一个进程只能服务一个人 |
| `web/server.py` `pending`、`_tickets` | 权限请求、SSE 票据存在进程内存 | 多副本时，请求落到另一台机器就找不到了 |
| `web/server.py` `ThreadingHTTPServer` | 每个连接一个线程，SSE 长连接一直占着线程 | 上千个浏览器长连接 = 上千个线程，标准库服务器不适合直接面向公网 |
| `events.py` `EventBus.history` | 内存里保留最近 2000 个事件，SSE 重连时补发 | 只在本进程有效；换机器或重启后刷新页面，历史丢失 |
| `session.py` `save()` | 会话存为 `~/.nanocode/projects/<目录>/sessions/*.json`，**一轮结束后才保存** | 本地磁盘不共享；任务进行到一半进程挂了，这一轮全部丢失 |
| `context.py` `home_dir()` | 全局 `~/.nanocode`：`settings.json`、`trusted.json`、trace 都在这里 | 所有用户共用一份配置和信任记录 |
| `session.py` `Options.cwd` | 工作目录是进程启动参数，整个进程只有一个 | 每个用户需要自己的工作区 |
| `tools/shell.py` `Bash` | `subprocess.Popen(["bash", "-c", ...])` 直接在宿主机执行 | 用户（或被提示词注入的模型）能读写宿主机、访问内网、读环境变量里的 API Key |
| `permissions.py` | 按字符串匹配规则放行或拒绝；第 04 章已说明它**不是安全边界** | 多租户下不能把安全寄托在它上面 |
| `mcp.py`、`hooks.py`、`verify.py` | 都会启动子进程执行命令 | 同上，必须在沙箱内 |
| `trust.py` | 第一次遇到项目敏感配置时，在终端问用户是否信任 | Web 多租户下没有"本机用户"可问；信任要变成管理员策略 |
| `llm/__init__.py` `make_provider` | API Key 来自进程环境变量，每个进程自己重试 | 所有用户共用一个 Key，没有按用户的限流、预算、计费；各进程各自重试，429 时会一起撞墙 |
| `rag.py` | 索引存为工作区里的 JSON 文件 | 跟着工作区走即可，但要算进磁盘配额 |

好消息是有几处设计天然适合扩展：

- **事件总线**：界面和 trace 都只是订阅者（第 01 章）。把事件发到 Redis、日志系统，只需要再写一个订阅者，不用改 Agent 核心。
- **事件带 `seq` 序号**：可以直接用来实现 SSE 断线续传（`Last-Event-ID`）。
- **`MockProvider` 支持 `delay`**：压测时可以模拟模型延迟，不花真实 token。
- **会话存档是纯 JSON 的消息列表**：迁移到数据库很直接（包括 #17 加的 `extra_content` 字段）。

## 二、容量估算

"1000 个用户"不等于"1000 个并发任务"。按下面的假设先算一个量级：

| 假设 | 取值 | 说明 |
|---|---|---|
| 注册 / 活跃用户 | 1000+ | 题目给定 |
| 高峰同时在线（页面开着） | 30%：约 300 | 每人一条 SSE 长连接 |
| 高峰同时在跑任务的会话 | 10%–20%：100–200 | 决定沙箱和 LLM 并发的规模 |
| 每个任务的步数 | 5–30 步 | `agent.py` 主 Agent 上限 60 步，子 Agent 30 步 |
| 每步模型调用 | 输入 5k–60k tokens，输出 0.2k–2k | 上下文越长输入越大；超过阈值会自动压缩 |
| 每个沙箱资源 | 0.5–2 vCPU，1–4 GB 内存，5–20 GB 磁盘 | 取决于用户跑什么（装依赖、跑测试最吃资源） |

由此得到几个要提前确认的数：

- **沙箱算力**：200 个并发 × 1 vCPU / 2 GB，约 200 vCPU、400 GB 内存，再加 30% 余量和预热池。
- **LLM 速率限制**：200 个会话、每个每 10–30 秒一次调用，峰值约 7–20 次/秒；按每次 30k 输入 token 算，约每分钟 1300 万–3600 万输入 token。**大多数厂商默认账号的 TPM 上限达不到这个量**，需要提前申请提额，或者分摊到多个厂商、多个账号。
- **成本**：每日成本 ≈ 日活任务数 × 平均步数 × 每步 token × 单价。必须有按用户的预算上限，否则少数用户的长任务就能把总预算用完。
- **长连接**：几百条 SSE 连接本身不大，但要选能处理大量空闲长连接的服务端（异步框架），并让负载均衡支持长连接和关闭缓冲。

### 关键决策：Agent 循环跑在哪里

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 一个会话一个沙箱（推荐先做）** | 每个活跃会话起一个沙箱，里面跑一份几乎不改的 nanocode（Agent 循环 + 工具 + 工作区）。控制面负责登录、路由、转发事件 | 改动最小：nanocode 假设"本地文件系统 + 进程内事件总线"，在沙箱里这些假设都成立；隔离边界清楚 | 每个会话都要占一个沙箱，空闲时也占资源（靠空闲回收和快照缓解）；冷启动有延迟（靠预热池缓解） |
| B. 循环与执行分离 | Agent 循环跑在共享的 worker 里，只有工具调用通过 RPC 发到沙箱执行 | 沙箱只在执行命令时需要，资源利用率更高 | 要把 `ToolContext`、`shell_cwd`、文件工具全部改成远程调用，改动大、出错面广 |

建议**第一阶段用方案 A 上线**，用真实用量数据判断资源利用率是否真的是瓶颈，再决定要不要演进到方案 B。

方案 A 有一个必须处理的坑：**沙箱里不能有真正的厂商 API Key**。模型可以执行 `env`、`cat /proc/self/environ`，被提示词注入后就能把 Key 发出去。正确做法是：沙箱只拿到一个**短期、只能访问 LLM 网关、绑定到这个会话**的令牌，真实 Key 只存在于 LLM 网关里。nanocode 这边只需要把 `base_url` 指向网关、`api_key` 换成会话令牌，代码不用改。

### 关于"纯标准库"

nanocode 核心坚持只用标准库，这是学习项目的特点，应该保留。分布式部署需要的东西（异步 Web 框架、数据库驱动、Redis 客户端、K8s 客户端、OIDC）放进一个**独立的包**（例如 `nanocode-server`），核心通过事件总线订阅者和少量扩展点接入。这样教程代码保持简洁，生产部署也不受限制。

## 四、分项改造计划

每一项列出：要做什么、为什么、涉及哪些代码。

### 4.1 执行隔离（P0，上线前必须完成）

- **每个会话一个沙箱**：用 gVisor（runsc）、Kata Containers 或 Firecracker 这类强隔离运行时，不要只用普通 Docker 容器（共享宿主机内核，逃逸风险高）。
- **资源限制**：CPU、内存、进程数（防 fork 炸弹）、磁盘配额、单条命令超时（`shell.py` 已有 600 秒上限）、整个会话的最长存活时间。
- **最小权限**：非 root 运行；根文件系统只读，只有工作区和 `/tmp` 可写；不挂载宿主机目录；不挂载 K8s ServiceAccount 令牌；禁止特权容器。
- **网络出口白名单**：默认拒绝所有出站，只放行 LLM 网关、包管理镜像（PyPI、npm 等）、用户明确配置的 git 仓库地址。**禁止访问云厂商元数据地址（169.254.169.254）和内网**。`web_fetch` 已有 SSRF 防护（第 04 章），但模型可以直接用 `bash` 里的 `curl` 绕过它，所以真正的防线必须在网络层。
- **权限模式策略**：在沙箱里，`bypass` 才变得可以接受。但仍建议默认用 `review` 模式（第 11 章）：低风险操作自动放行，高风险操作要确认，并且有改动汇总。由管理员策略决定用户能选哪些模式。
- **项目配置信任**：`trust.py` 现在会问本机用户。多租户下改成：用户自己的工作区默认信任（反正在沙箱里），`mcpServers` 只允许管理员白名单里的服务器，`provider`、`base_url`、`headers` 这类改变请求去向的配置**一律由平台决定，不允许用户覆盖**，否则用户可以绕过 LLM 网关的计费和审计。
- **涉及代码**：`trust.py`（增加"平台策略"这一层，优先级高于项目配置）、`session.py` `load_settings`（读平台策略）、`permissions.py`（限制可选模式）。沙箱本身是基础设施，不在 nanocode 代码里。

### 4.2 身份认证与多租户（P0）

- **登录**：接企业 SSO（OIDC / SAML）或第三方登录，在控制面完成。用 HttpOnly、Secure、SameSite=Lax 的会话 Cookie，加 CSRF 防护，替代现在注入页面的全局令牌。
- **授权**：每个请求校验"这个用户是否拥有这个会话"。所有接口改成 `/api/sessions/{id}/...` 的形式，按会话 ID 路由。`/api/context` 会返回完整的系统提示词和对话，尤其要做好授权。
- **租户模型**：组织 → 用户 → 会话 → 工作区。配额、预算、模型白名单可以按组织和用户设置。
- **角色**：普通用户、组织管理员（配额、成员、策略）、平台管理员（全局策略、审计、紧急停用）。
- **涉及代码**：`web/server.py` 的 `WebApp` 从"一个会话"改成"会话管理器"，或者在方案 A 下保持 `WebApp` 不变、只在沙箱内部使用，由控制面完成认证后再转发。后者改动更小，推荐。

### 4.3 状态外置（P0 / P1）

| 状态 | 现在 | 改成 | 优先级 |
|---|---|---|---|
| 会话消息、待办、用量 | 本地 JSON，一轮结束才保存 | PostgreSQL（消息块用 JSONB 存，保留 `extra_content` 等字段）；**每一步结束都保存** | P0 |
| 事件流（SSE 补发） | 进程内 `deque` | Redis Streams，按会话一个流；用事件的 `seq` 支持 `Last-Event-ID` 断线续传；设置长度上限和过期时间 | P1 |
| trace | 本地 JSONL 文件 | 结构化日志管道或对象存储；设置保留期限 | P1 |
| 工作区 | 进程启动时的 `cwd` | 每个会话一个持久卷；空闲时打快照存到对象存储，恢复时还原 | P0 |
| 权限请求、SSE 票据 | 进程内存 | 方案 A 下留在沙箱内即可；如果控制面多副本需要处理它们，放进 Redis 并设 TTL | P1 |
| 用户配置、信任记录 | `~/.nanocode/settings.json`、`trusted.json` | 数据库里的组织 / 用户策略表 | P1 |
| 项目记忆 `NANOCODE.md` | 工作区里的文件 | 不变，随工作区走 | — |

**"每一步保存"很重要**：`Session.send()` 现在在 `agent.run()` 整轮结束后才调用 `save()`。一个 30 步的任务，进行到第 29 步时沙箱被回收或节点故障，整轮全部丢失。分布式环境下节点故障是常态，必须改成每一步（每次 `llm_response` / `tool_result` 之后）增量保存。用事件总线订阅者实现最自然，不需要改 Agent 循环。

### 4.4 会话调度与生命周期（P0）

- **按需创建**：用户打开或恢复会话时创建沙箱；从快照还原工作区，从数据库还原消息（相当于现在的 `--resume`）。
- **预热池**：保持一批已启动的空白沙箱，把冷启动从几十秒降到几秒。
- **空闲回收**：一段时间（例如 15–30 分钟）没有任务、也没有等待中的权限确认，就把工作区打快照、销毁沙箱。
- **准入控制**：总容量满时，新任务排队并在界面上显示排队位置，而不是直接失败；每个用户限制同时运行的会话数（例如 2–3 个）。
- **路由**：控制面在 Redis 里维护"会话 ID → 沙箱地址"，SSE 和 API 请求按这个转发。
- **优雅下线**：节点要下线时，先停止接新任务，等运行中的任务结束或在安全点保存后再迁移。
- **权限等待占资源**：`nanocode_server` 中 `WebApp.ask()` 默认最多等待 10 分钟，等待期间沙箱一直占着。当前服务器没有单独的权限等待超时配置，也不会把 `NANOCODE_PERMISSION_TIMEOUT` 传入会话沙箱；缩短等待时间需要为平台增加受控配置，或者在等待期间把沙箱降配。

### 4.5 LLM 网关与成本控制（P0）

- **集中管理 Key**：真实 Key 只存在网关里，可以有多个 Key 和多个厂商组成的池子。
- **按用户 / 组织限流和预算**：令牌桶（存在 Redis）限制请求速率；按日、按月的 token 预算，超了就拒绝并明确提示。复用现有的 `QuotaExhausted` 语义，让界面显示"额度已用完"而不是一般错误。
- **全局排队与退避**：现在每个进程各自重试（`llm/base.py`，最多 3 次指数退避），几百个会话同时遇到 429 会同时重试、互相加剧。网关统一排队、统一退避，必要时切换到备用厂商。
- **计量**：从每次响应的 `usage` 记录用户、会话、模型、输入输出 token、缓存命中，写入数据库，用于计费和成本分析。
- **省钱手段**：开启提示词缓存（`AnthropicProvider` 已支持 `prompt_cache`）；系统提示词和工具定义保持稳定以提高缓存命中；按任务类型选模型（子 Agent 用更便宜的模型）；必要时调低压缩阈值。
- **紧急开关**：一键停用某个用户、某个模型或全部任务。
- **数据合规**：用户代码会发给第三方模型厂商。要确认厂商的数据使用条款（是否用于训练、保留多久），签好数据处理协议；涉及跨境传输时符合当地法规（如个人信息保护法、GDPR）。

### 4.6 安全加固（P0）

除了 4.1 的沙箱，还要处理这些：

- **提示词注入导致的数据外传**：恶意网页、依赖包、仓库里的文件都可能包含指令。出口白名单是主要防线，界面上对高风险操作的确认（`review` 模式）是第二道。
- **跨租户访问**：命名空间、存储卷、数据库行级权限都按租户隔离，并写自动化测试专门验证"A 用户访问 B 的资源一定失败"。
- **滥用**：挖矿、发垃圾邮件、拿沙箱当跳板攻击别人。靠 CPU 配额、出口白名单、异常检测（CPU 长期打满、出站流量异常），以及服务条款。
- **审计日志**：每次工具调用、权限决策、配置变更都记录下来，写入只追加的存储。事件总线里已经有 `tool_call`、`permission` 事件，加一个订阅者导出即可。
- **数据安全**：传输和存储全程加密；设定数据保留期限；支持用户导出和删除自己的数据。
- **供应链**：沙箱镜像固定版本并做漏洞扫描；MCP 服务器只用白名单里的。
- **上线前**：做威胁建模、找第三方做渗透测试、专门测试沙箱逃逸和跨租户访问。

### 4.7 可观测性（P1）

- **指标**：活跃会话数、排队长度、沙箱启动耗时、模型首字延迟和总耗时、各厂商错误率和 429 次数、每用户 token 和成本、工具执行耗时、自动验证通过率（第 11 章）。
- **日志**：结构化 JSON，每条都带 `user_id`、`session_id`、`trace_id`。
- **链路追踪**：用 OpenTelemetry 把 `llm_request`、`tool_call` 做成 span，能看清一个任务慢在哪一步。
- **SLO 示例**（按实际情况调整）：服务可用性 99.5%；模型首字延迟 p95 小于 5 秒（不含厂商故障）；沙箱就绪 p95 小于 10 秒。
- **告警和预案**：厂商故障或额度耗尽、沙箱节点故障、数据库或 Redis 主从切换、成本异常飙升，每种情况都要有写好的处理步骤。

### 4.8 前端与产品体验（P1）

- 会话列表：新建、恢复、重命名、删除；一个用户可以有多个会话。
- 断线续传：SSE 带 `Last-Event-ID`，刷新或断网重连不丢事件。
- 状态可见：排队位置、沙箱启动中、额度剩余。
- 工作区文件：上传、下载、从 git 仓库克隆（用户的 git 凭证要加密保存，只在沙箱内短期使用）。
- 权限确认在移动端也要能用；默认 `review` 模式减少打断。

### 4.9 测试与发布（贯穿全程）

- **压测**：用 `MockProvider` 加 `delay` 模拟模型延迟，不花 token，压控制面、事件流、沙箱调度。目标：200 个并发任务、1000 条 SSE 连接下稳定运行。
- **故障演练**：随机杀沙箱、杀控制面副本、断开 Redis、让 LLM 网关返回 429 或 503，验证任务能恢复、用户能看到明确的状态。
- **安全测试**：沙箱逃逸、跨租户访问、出口白名单绕过、提示词注入红队（可以基于 `evals/` 加注入类任务）。
- **评测回归**：每次升级模型或改提示词，用 `evals/agent_tasks` 跑一遍真实模型，对比成功率和成本。
- **分批放量**：内部 20–50 人 → 公测 200 人 → 正式开放 1000+ 人。每一批设好退出标准，用功能开关和金丝雀发布，随时可以回滚。

## 七、待决定的问题

这些问题会直接影响架构和成本，需要尽早定下来：

1. **谁付模型费用**：平台统一付费，还是用户自带 Key？前者需要完整的计量和预算体系；后者要安全保存用户的 Key，并且仍然要防止 Key 在沙箱里泄露。
2. **用户的代码从哪来**：只在沙箱里新建项目，还是连接用户的 GitHub / GitLab？后者涉及 OAuth 授权和凭证管理。
3. **部署在哪里、数据存在哪里**：决定能用哪些模型厂商，以及要满足哪些合规要求。
4. **沙箱技术**：gVisor 部署最简单；Firecracker 隔离最强、启动最快，但运维复杂。取决于团队经验和云厂商支持。
5. **是否允许用户自定义 MCP 服务器和 hooks**：允许会带来更大的攻击面，不允许会限制能力。建议先只开放白名单。

## 九、实现状态

方案 A 已经实现成可以运行的平台：nanocode 本体的改动在 `nanocode/` 里，控制面和模型网关是独立的包 [`server/`](../server/README.md)，镜像和 Kubernetes 清单在 [`deploy/`](../deploy/)。一台电脑上就能跑：

```bash
PYTHONPATH=server:. python3 -m nanocode_server               # 打开 http://127.0.0.1:8700，登录页输入任意用户名
PYTHONPATH=server:. python3 -m nanocode_server demo --users 10   # 模拟 10 个用户同时使用，检查互相隔离
```

可选组件有就用、没有也能跑：数据库 SQLite / PostgreSQL，限流 内存 / Redis，沙箱 本机进程 / Docker / Kubernetes。页面上可以添加自己的 API Key、为每个会话切换模型；Key 加密保存，只在模型网关里使用，不会进入沙箱。
