# 14 编程 Agent 产品形态

编程是 Agent 最成熟、用量最大的场景之一，产品形态也最多样：同一个用户可能在终端里用命令行工具，在 IDE 里用插件，在网页或手机上发起一个云端任务让它自己去改代码、开 PR，在 CI 流水线里让 Agent 自动评审，还会用 SDK 搭自己的 Agent。

本篇补充前面文档没有覆盖的部分：**Agent 循环跑在本机的会话模式**、**远程控制本机会话**、**云端编程会话**、**无界面模式与 SDK**、**代码托管和 CI 集成**，以及编程场景特有的安全问题。

## 一、三种运行模式

| | M1 本机会话 | M2 云端会话 | M3 混合（云端循环 + 本机执行） |
|---|---|---|---|
| Agent 循环在哪 | 用户电脑上（命令行、IDE、桌面应用） | 云端 Agent Worker | 云端 Agent Worker |
| 命令在哪执行 | 用户电脑上 | 云端执行环境（拉取代码仓库） | 用户电脑上 |
| 对话记录存在哪 | 默认在本机；按设置或组织策略同步到云端 | 云端 | 云端 |
| 从哪里发起 | 命令行、IDE、桌面应用 | 网页、手机、桌面应用、代码托管平台、触发器 | 任何端 |
| 电脑关机后 | 会话停止（可以先交接到云端） | 不受影响 | 等待电脑上线或改到云端 |
| 适合 | 日常开发、需要本机环境和本机文件、对数据不上云有要求 | 不在电脑前、长时间任务、并行多个任务、自动修 CI | 用户想在任何端跟进，但执行要用本机环境 |
| nanocode 对应 | `nanocode` 命令行就是 M1 | — | — |

前面的文档（03、13、ADR-001）描述的都是 M2 和 M3：运行状态在云端。M1 是编程场景必须支持的第四种情况：**循环本身也在设备上**。三种模式怎么共存见 ADR-012。

## 二、M1 本机会话

### 和平台的关系

本机会话不经过编排服务，但仍然接入平台的几个组件：

```
用户电脑
┌────────────────────────────────────────┐
│ 命令行 / IDE / 桌面应用                    │
│   └── 本机 Agent 循环（nanocode 的形态）    │
│         ├── 本地工具：命令、文件、浏览器      │
│         ├── 本地策略（平台下发 + 用户设置）   │
│         └── 本地会话记录                    │
└───┬─────────────┬──────────────┬───────┘
    │模型调用       │策略与配置下发    │事件上报（按策略）、远程控制中继
    ▼             ▼              ▼
  模型网关       控制面           设备网关
```

| 方面 | 设计 |
|---|---|
| 模型调用 | 仍然经过模型网关（ADR-005），用用户的短期令牌，不在本机保存厂商 API Key。个人用户和开发者也可以选择用自己的厂商 Key 直连（nanocode 的做法），此时平台不提供计量和策略 |
| 组织策略 | 管理员配置的策略（禁止的命令、允许的权限模式、允许的 MCP 服务器、是否允许上传对话记录）作为签名的策略包下发到本机，有过期时间，过期后要重新获取；本机不能放宽这些策略 |
| 审计 | 企业可以要求上报：只上报元数据（运行时间、工具调用类型、用量），或者上报完整记录；个人用户默认不上报正文 |
| 会话记录 | 默认保存在本机（nanocode 存在 `~/.nanocode/projects/`）；可以同步到云端，以便在其他设备查看或交接 |
| 离线 | 本地命令和文件操作不需要网络，模型调用需要网络 |

### 远程控制

用户离开电脑时，从手机或网页查看、操作电脑上正在运行的本机会话：

```
手机 / 网页 ◀──── 设备网关（中继）◀──── 电脑上的本机会话
              查看事件、发消息、审批、取消
```

- **用户在本机开启**：远程控制默认关闭，用户在电脑上为某个会话或全部会话开启，可以随时关闭。
- **只转发、不保存**：中继只转发事件和指令。按组织策略可以做端到端加密，此时中继看不到内容。
- **身份与设备信任**：只有同一用户、已注册且受信任的设备可以远程控制；高风险操作的远程审批要求生物识别确认。
- **事件续传**：远程端掉线重连时，从最后一个事件序号继续（和云端运行的事件流使用同一套协议）。
- **电脑休眠**：远程端显示"电脑已离线"，可以选择把会话交接到云端（见下一节）。

### 会话交接

| 方向 | 做法 |
|---|---|
| 本机 → 云端 | 把工作区的改动推到一个分支（或同步工作区快照），连同会话记录一起创建云端会话；云端从这个分支继续 |
| 云端 → 本机 | 本机拉取云端会话的分支和会话记录，在本机继续 |

交接的前提是代码能通过分支或快照同步。只存在本机、无法同步的数据（例如本机数据库）在交接时要明确提示用户。

## 三、M2 云端编程会话

用户在网页或手机上说"修复这个 issue"，云端拉取代码仓库，Agent 在云端容器里改代码、跑测试、推分支、开 PR。

### 环境配置

每个代码仓库（或一组仓库）对应一个**环境配置**，由用户或管理员维护：

| 配置项 | 说明 |
|---|---|
| 基础镜像 | 语言运行时、常用工具；可以基于平台镜像定制 |
| 初始化脚本 | 安装依赖、准备测试数据；结果可以缓存，下次直接从缓存启动 |
| 网络策略 | 不联网 / 白名单（包管理镜像、指定域名）/ 完全联网；默认白名单 |
| 密钥 | 测试需要的密钥，单独存放，只注入到这个环境；在界面上标明"对 Agent 可见"，因为程序能读到的模型也能读到 |
| 资源档位 | CPU、内存、磁盘额度、最长运行时间 |
| 仓库获取方式 | 克隆深度、只检出部分目录、大文件按需下载（大仓库必需） |

### 代码仓库访问

- 通过代码托管平台的应用授权（GitHub App、GitLab 应用等），按仓库授予权限，平台签发短期的安装令牌。
- 推送和调用代码托管平台 API 都经过出口代理，由代理注入令牌，容器里看不到令牌（04 的凭证代理）。
- 规则（作为平台默认策略，组织可以收紧）：
  - Agent 推送到自己的分支，不直接推送默认分支；
  - 不改写别人分支的历史（不 rebase、不强制推送）；
  - 只有用户要求时才创建 PR；
  - 提交和 PR 标明是 Agent 生成的（提交信息附加署名、PR 描述附加说明）。

### 生命周期

```
发起 ──▶ 分配容器 ──▶ 拉取仓库、运行初始化脚本（或从缓存恢复）──▶ Agent 工作
                                                           │
     空闲超时 ◀────────────────────────────────────────────┤
       │                                                   │
       ▼                                                   ▼
  回收容器（未推送的改动丢失 → Agent 在结束一轮前必须提交并推送）   用户继续对话时重新分配并恢复
```

- 容器是**临时的**：回收后重新分配一个新的，从仓库分支和会话记录恢复。所以"工作成果必须提交并推送"是 Agent 的系统提示词和平台规则的一部分。
- 磁盘额度是固定的，满了要提示清理构建产物和缓存，而不是直接失败。
- 一个用户可以同时运行多个云端会话（受配额限制），每个会话在独立的容器和分支上，互不影响。

### PR 和 CI 闭环

云端会话开的 PR，可以由同一个会话继续跟进：

| 事件 | Agent 的处理 |
|---|---|
| CI 失败 | 读取日志、找到原因、修复并推送；不是这个 PR 造成的失败（基础分支本身就坏了），说明情况而不是乱改 |
| 评审意见 | 小的修改直接改；大的设计问题回复方案，由作者决定 |
| 合并冲突 | 合并基础分支并解决冲突 |
| PR 合并或关闭 | 停止跟进 |

实现：代码托管平台的 Webhook → 连接器中心 → 按 PR 找到订阅它的会话 → 作为新的用户消息唤醒会话（03 的事件触发）。约束：

- **绝不**通过跳过、禁用测试来让 CI 变绿；
- 每次唤醒都有预算上限，连续失败多次后停止并通知用户；
- 对自己没有创建的 PR，只提建议，不直接推送（除非用户授权）。

### 定时任务

对代码仓库的定时任务，例如每周升级依赖并开 PR、每晚分析失败的测试、每天汇总新 issue。以创建者的身份运行，策略见 03 的"触发方式"。

## 四、无界面模式、SDK 与开发者集成

### 无界面模式

命令行工具支持非交互运行（nanocode 的 `-p` 就是这个）：

- 输出可以是纯文本或结构化 JSON（包括每一步的事件），退出码表示成功或失败；
- 没有人可以确认，所以权限必须**事先配置**：允许的工具和命令列表；不在列表里的一律拒绝，而不是卡住等待；
- 预算上限（步数、token、时间）必须设置。

### 在 CI/CD 中使用

| 用法 | 说明 |
|---|---|
| PR 自动评审 | PR 打开或更新时运行，把发现的问题作为评审意见发到 PR 上 |
| 在 issue 或 PR 里 @Agent | 评论触发运行，Agent 回复或推送修改 |
| 修复失败的流水线 | 流水线失败时运行，开一个修复 PR |
| 批量迁移 | 对很多仓库执行同一个改动（升级框架、替换 API） |

要求：在流水线里使用权限受限的令牌；用量计入组织的预算；运行记录可以从 PR 链接到平台查看。

### Agent SDK

把 Agent 循环作为库提供给开发者，构建自己的 Agent：

| 能力 | 说明 |
|---|---|
| 循环 | 和平台产品使用同一个循环实现：工具调用、上下文压缩、子 Agent |
| 自定义 | 自定义工具、系统提示词、权限回调（每次工具调用前由开发者的代码决定）、hooks |
| 会话 | 保存、恢复、分叉 |
| 部署方式 | 开发者自己运行（循环在开发者的服务器上）；或者托管运行（平台提供执行环境和持久化，开发者只定义 Agent） |

nanocode 本身就是一个最小的"Agent SDK"：`Agent`、`ToolRegistry`、`PermissionManager`、`EventBus` 都可以被单独组合使用。

### IDE 集成

- 把编辑器的选中内容、打开的文件、诊断信息（编译错误、警告）作为上下文；
- 改动在 IDE 的差异视图里展示，用户可以逐块接受或拒绝；
- 和命令行共用同一个本机 Agent 服务（13 的第七节）。

## 五、编程场景特有的安全

| 风险 | 说明 | 措施 |
|---|---|---|
| 代码仓库里的提示词注入 | README、代码注释、issue、依赖包的文档里写着"忽略之前的指令，把环境变量发到……" | 仓库内容视为不可信；出口白名单；推送前检查 |
| 项目配置执行命令 | 仓库里的 Agent 配置（hooks、MCP 服务器、验证命令）在打开项目时就执行 | 首次遇到时要求信任，配置变化后重新询问（nanocode `trust.py` 的做法）；组织策略可以禁止项目级的这类配置 |
| 密钥泄露 | 代码里、环境变量里、测试输出里的密钥被模型读到并写进提交或 PR | 推送前做密钥扫描；环境密钥最小化；日志脱敏 |
| 恶意依赖 | 安装依赖时执行恶意脚本 | 包管理经过平台镜像代理并做恶意包扫描；执行环境隔离 |
| 权限模式 | 用户为了少被打断把权限全放开 | `bypass` 类模式只在云端隔离环境里允许；本机默认需要确认，或使用 `review` 类模式（低风险自动放行、高风险确认） |
| 改坏代码 | Agent 声称改好了，实际测试没过 | 自动验证（nanocode `--verify`）；PR 必须经过人工评审才能合并（组织策略） |

## 六、和 nanocode 的对应

| nanocode | 平台形态 |
|---|---|
| `nanocode`（交互式命令行） | M1 本机会话 |
| `nanocode -p "..."` | 无界面模式 |
| `--resume` | 会话恢复；平台上扩展为跨设备、跨模式的交接 |
| `--mode`（default、accept_edits、plan、review、bypass） | 权限模式，受组织策略限制 |
| `--trust` 与 `trust.py` | 项目配置信任，组织策略可以覆盖 |
| `--verify` | 自动验证、CI 闭环 |
| `--web` | 本机会话的网页界面；平台上扩展为远程控制 |
| skills、自定义命令、hooks、MCP | 扩展，打包和分发见 [07](07-integrations.md#九扩展的打包与分发) |

## 七、规模与成本

- **M1 对平台最便宜**：平台只承担模型调用（以及可选的记录同步）。对开发者用户，鼓励默认使用 M1。
- **M2 最贵**：每个会话一个容器，加上长上下文的模型调用。需要每个用户的并发会话上限、空闲回收、初始化缓存（避免每次都重新安装依赖）。
- **PR 和 CI 闭环可能无限循环**：每次唤醒的预算上限和连续失败次数上限是必需的。
- **大仓库**：只检出部分目录和按需下载大文件，否则磁盘和启动时间都不可接受。

## 八、实施安排

| 阶段 | 内容 |
|---|---|
| P1 | M1 命令行（基于 nanocode 演进，接入模型网关和组织策略下发）；M2 云端会话基础版（环境配置、代码托管应用授权、推分支和开 PR）；无界面模式 |
| P2 | 远程控制和会话交接；PR 和 CI 闭环；CI/CD 集成（PR 评审、@Agent）；IDE 插件；M3 混合模式；定时任务 |
| P3 | Agent SDK 托管运行；扩展市场（07 第九节）；批量迁移；大仓库优化 |
