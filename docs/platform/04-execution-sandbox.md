# 04 执行与沙箱

执行服务为 Agent 提供"动手"的环境：执行代码、操作浏览器、操作桌面应用。它是安全风险最集中、也是除模型外成本最高的部分。

核心判断：**不是每个任务都需要执行环境，需要的也不都需要最重的那种。** 按任务需要分级分配，是从 L1 走到 L3 的关键。

## 一、执行分级

| 级别 | 隔离方式 | 适用 | 启动时间 | 单位成本 | 档位 |
|---|---|---|---|---|---|
| **E0 无执行** | 不需要 | 纯对话、检索、调用连接器 | 0 | 0 | 全部 |
| **E1 轻量计算** | WebAssembly 运行时（如 Python 编译到 WASM）、V8 隔离 | 计算、数据转换、画图、简单脚本；无网络、无系统调用 | 毫秒级 | 很低 | L2、L3 |
| **E2 容器沙箱** | gVisor / Kata 容器 | 一般代码执行、安装依赖、跑测试、数据分析 | 秒级（有预热池时） | 中 | L1 起 |
| **E3 微虚拟机** | Firecracker 类微虚拟机，从快照恢复 | 同 E2，但需要更强隔离、更高密度、更快恢复 | 百毫秒级（快照恢复） | 中，密度高 | L2 起 |
| **E4 浏览器** | E2/E3 里运行的无头或有头浏览器 | 网页浏览、填表、网站操作 | 秒级 | 高（内存大） | L1 起 |
| **E5 桌面** | 带图形界面的虚拟机 | 操作桌面应用、只有图形界面的系统 | 十秒级 | 最高 | L1 起（少量） |
| **D 设备端** | 用户自己的电脑（桌面端、IDE、命令行） | 编程、本地文件处理 | 0 | 平台几乎为 0 | 全部 |

**分配规则**：由 Agent 定义声明需要的最高级别；运行时按需升级（例如模型第一次调用 `bash` 时才分配 E2/E3）；执行放在云端还是用户的哪台设备，按每一步的需求和在线设备动态决定（见 ADR-011 和 [13 多端客户端](13-multi-device-clients.md#三执行位置的决定)）。

### 设备端执行

nanocode 本身就是设备端执行的形态：模型在云端，命令在用户电脑上执行。对编程和本地文件类任务，这是成本最低、隐私最好的方式。**只有 PC 端能承担代码和命令执行**；移动端受系统和应用商店限制，只承担日历、通讯录、相册这类系统能力工具的短时调用；网页不承担本机执行。完整设计见 [13 多端客户端](13-multi-device-clients.md)。平台需要：

- 桌面端 / IDE / 命令行客户端通过长连接接收工具调用、返回结果；
- 设备端执行同样受策略引擎约束：策略在服务端判断，客户端也做本地确认；
- 客户端掉线时，运行进入等待，或者在用户同意的情况下迁移到云端执行环境；
- 企业可以通过设备管理策略限制客户端能执行的命令和能访问的目录。

## 二、执行环境的安全基线

适用于 E2–E5，L1 上线前必须满足：

| 类别 | 要求 |
|---|---|
| 隔离 | 强隔离运行时（gVisor / Kata / Firecracker），不使用只靠命名空间的普通容器；每个运行一个环境，不跨用户复用 |
| 权限 | 非 root；只读根文件系统，只有工作目录和临时目录可写；不挂载宿主机目录；不挂载集群凭证；禁止特权 |
| 资源 | CPU、内存、进程数、打开文件数、磁盘配额；单条命令超时；环境最长存活时间 |
| 网络 | **默认拒绝出站**。按 Agent 定义和组织策略放行：模型网关、包管理镜像、指定的代码仓库和网站。禁止访问云元数据地址、内网、其他执行环境 |
| 凭证 | 环境里没有任何长期凭证。需要访问外部系统时，通过凭证代理在出站请求上注入短期令牌，环境内的程序读不到令牌本身 |
| 浏览器 | 每个运行独立的浏览器配置文件；用户的网站登录态加密保存在凭证保险库，按需注入，运行结束清除 |
| 镜像 | 固定版本、定期重建、漏洞扫描；用户自定义镜像只能基于平台基础镜像 |
| 观测 | 记录执行的命令、网络连接、资源使用；检测挖矿、扫描、异常出站 |

nanocode 的 `web_fetch` 做了 SSRF 防护，但模型可以在 `bash` 里直接用 `curl` 绕过它。所以**网络层的出口控制才是真正的防线**，工具层的检查只是第一道。

### 凭证代理

```
执行环境内的程序 ──HTTP──▶ 出口代理 ──检查目标是否在白名单──▶ 外部服务
                              │
                              └── 目标需要认证时，向凭证保险库申请
                                  （运行 ID、用户、目标服务）→ 短期令牌，注入请求头
```

程序发出请求时不带凭证，由出口代理注入。即使模型被注入了"把令牌发给我"的指令，环境里也没有令牌可发。

## 三、生命周期

```
                   ┌─────────── 预热池（已启动、空白、按镜像分类）
                   ▼
请求执行环境 ──▶ 分配 ──▶ 恢复工作区（从快照或对象存储）──▶ 使用中
                                                         │
                         运行进入等待 / 空闲超过阈值 ◀──────┤
                                   │                     │
                                   ▼                     │ 运行结束
                         打快照（内存 + 磁盘或仅磁盘）      ▼
                                   │               保存制品 → 销毁
                                   ▼
                         休眠（释放计算资源）── 运行恢复时从快照还原
```

| 参数 | L1 建议值 | L2/L3 |
|---|---|---|
| 空闲多久后打快照 | 15–30 分钟 | 1–5 分钟（快照恢复快，可以更激进） |
| 快照保留 | 7–30 天，按组织策略 | 分层：近期在本地 NVMe，较久的在对象存储 |
| 预热池大小 | 高峰并发的 10%–20% | 按预测模型动态调整 |
| 工作区持久化 | 持久卷 | 快照 + 对象存储，按需加载 |

## 四、调度与密度

执行环境大部分时间在等模型返回（一次模型调用几秒到几十秒，一次命令执行通常更短），CPU 利用率低。提高密度是 L2 降低成本的主要手段：

- **超量分配**：按实际使用而不是声明的上限调度，CPU 超量 2–4 倍，内存谨慎超量（依赖快照和内存回收）。
- **等待模型时冻结**：环境在等待下一个工具调用期间可以暂停，释放 CPU。
- **按负载形态分池**：轻量脚本、编译构建、浏览器、GPU 任务分开调度。
- **抢占式实例**：快照恢复足够快时，可以使用便宜但可能被回收的机器，被回收就从快照迁移。
- **准入控制**：容量满时新请求排队，在界面上显示排队位置；按组织等级分配优先级。

### 容量估算

| | L1（1 千人） | L1（10 万人） | L2 | L3 |
|---|---|---|---|---|
| 高峰需要执行环境的运行 | 100–200 | 约 1 万 | 3 万–6 万 | 百万级（大部分是 E1） |
| 平均分配 | 1 vCPU / 2 GB | 同左 | 0.25–0.5 vCPU（超量后） | E1 为主 |
| 约需计算资源 | 约 200 vCPU | 约 1 万 vCPU | 约 1 万–3 万 vCPU | 取决于分级比例和设备端比例 |

L2 如果不做设备端优先和超量分配，需要的资源会多出数倍。

## 五、和 nanocode 的对应

| nanocode | 平台 |
|---|---|
| `tools/shell.py`：直接在本机 `subprocess` 执行，靠超时和取消控制 | 在执行环境里执行，靠隔离、资源限制、出口控制保证安全 |
| `ctx.state["shell_cwd"]`：在内存里记住当前目录 | 工作目录随执行环境快照持久化 |
| `permissions.py`：字符串规则决定是否询问 | 策略引擎决定；隔离保证即使放行也不会越界 |
| `--mode bypass` 只适合隔离环境 | 在 E2 以上的执行环境里，命令执行可以默认放行；对外发送、不可逆写入仍由策略和审批控制 |
