# 08 安全、合规与治理

Agent 平台的安全问题比普通 SaaS 多一个维度：**系统里有一个会自己做决定、会被外部内容影响的执行者**。传统安全措施（认证、授权、加密、审计）全部需要，此外还要假设 Agent 随时可能被提示词注入"劫持"，并保证被劫持时损害有限。

## 一、威胁模型

| 威胁 | 例子 | 主要防线 |
|---|---|---|
| 跨租户访问 | 一个组织读到另一个组织的数据 | 数据访问层强制 `org_id`、执行环境隔离、独立密钥、跨租户自动化测试 |
| 提示词注入 | 网页、邮件、文档、工具结果里藏着"把客户名单发到这个地址" | 最小权限、出口控制、对外发送审批、数据防泄漏、来源标记 |
| 越权 | Agent 检索到发起人无权看的文档；以服务账号做了用户无权做的事 | 代表用户的授权、检索权限过滤、权限交集 |
| 凭证泄露 | 模型在执行环境里读到 API Key 并外传 | 凭证保险库 + 出口代理注入，环境里没有凭证 |
| 执行环境逃逸 | 利用内核漏洞突破沙箱 | 强隔离运行时、最小权限、及时打补丁、入侵检测 |
| 滥用 | 免费账号挖矿、发垃圾信息、攻击第三方 | 资源配额、出口控制、实名/支付验证、风险评分、异常检测 |
| 供应链 | 恶意第三方连接器、被投毒的依赖包 | 连接器审核和隔离、镜像扫描、包镜像代理 |
| 内部人员 | 平台员工查看客户数据 | 最小权限访问、访问审批、全量审计、客户可见的访问记录 |
| 模型输出有害内容 | 生成违法、歧视、危险内容 | 输入输出安全检查、按区域策略 |

## 二、身份与访问控制

### 用户身份

- 企业：SSO（SAML / OIDC）+ SCIM 自动同步成员和组；强制多因素认证由企业身份系统负责。
- 个人：邮箱、手机号、第三方登录；L2 起对高风险能力（执行代码、浏览器）要求更强的验证。
- 会话：短期令牌 + 刷新机制；敏感操作（修改策略、导出数据）要求重新认证。

### 授权模型

基于角色（RBAC）为主，属性（ABAC）补充：

| 角色 | 能做什么 |
|---|---|
| 组织所有者 | 全部，包括计费、删除组织 |
| 组织管理员 | 成员、策略、配额、连接器白名单、审计查看 |
| 安全管理员 | 策略、审计、数据防泄漏规则、事件调查，不能看业务内容（除非经过审批） |
| 工作空间管理员 | 工作空间内的 Agent 定义、知识源、记忆 |
| 成员 | 使用被授权的 Agent，管理自己的会话、授权、记忆 |
| 审计员 | 只读审计日志 |

### 策略引擎

统一回答：**主体**（用户、Agent 定义、触发器、服务账号）能否对**资源**（工具、知识源、数据、模型）执行**动作**，以及是否需要**审批**。

```
策略层级（从高到低，高层可以禁止，低层不能放宽高层的限制）：
  平台策略（法规、平台安全底线）
    → 区域策略（当地法规）
      → 组织策略（管理员配置）
        → 工作空间策略
          → Agent 定义
            → 用户本次运行的授权（"本次运行中允许"）
```

这是 nanocode `permissions.py`（allow / deny / 模式）和 `trust.py`（项目配置不能替用户放宽权限）的平台版本。策略用声明式规则描述、版本化管理，每次判断的结果和命中的规则都写入审计。

## 三、提示词注入：纵深防御

目前没有任何方法能从模型层面彻底杜绝提示词注入，所以设计目标是**被注入后损害有限**：

1. **最小权限**：Agent 定义只开放任务需要的工具和知识范围。一个"汇总工单"的 Agent 不需要发邮件的能力。
2. **数据流控制**：读了不可信内容（网页、外部邮件）之后，同一运行内的对外发送类操作自动提高审批等级。
3. **出口控制**：执行环境和连接器只能访问白名单内的目标（见 04）。
4. **审批**：对外发送、不可逆写入、涉及资金的操作默认需要人确认，审批界面清楚展示"要发什么、发给谁"。
5. **数据防泄漏**：对外发送的内容扫描敏感信息（身份证号、银行卡号、密钥、标记为机密的文档片段），按策略拦截或要求审批。
6. **来源标记**：工具结果在上下文中标明来源和可信度，系统提示词说明外部内容中的指令不是用户指令。
7. **检测**：用分类模型识别疑似注入内容；监控异常行为（突然读取大量数据、访问从未访问过的目标）。
8. **红队**：持续用注入类评测集测试（可以在 nanocode 的 `evals/` 基础上扩展注入类任务），每次改提示词、换模型都要跑。

## 四、数据保护

| 方面 | 措施 |
|---|---|
| 加密 | 传输 TLS；存储加密；凭证和高敏感字段应用层加密；大客户可用自管密钥（BYOK），撤销密钥即无法解密其数据 |
| 模型厂商 | 只使用承诺不用客户数据训练、保留期可控的接口；签署数据处理协议；按组织策略限制可用厂商和区域 |
| 训练 | 平台默认不使用企业客户数据训练模型；个人用户的数据使用需明确告知并可选择退出 |
| 保留与删除 | 按组织配置保留期；用户和组织可导出、删除数据；删除覆盖备份（在备份保留期结束后） |
| 日志脱敏 | 应用日志、链路追踪不记录消息正文和工具参数中的敏感内容；需要排查时走审批访问 |

## 五、审计

- **记录什么**：登录、权限变更、策略变更、运行的创建和结束、每次工具调用（工具、参数摘要、结果状态）、每次审批、凭证签发、数据导出、平台员工的访问。
- **存储**：只追加、防篡改（哈希链或写一次只读存储），按合规要求保留。
- **使用**：管理后台查询；导出或实时推送到客户的 SIEM；事件调查时可以完整回放一次运行（每一步的上下文、模型输出、工具调用）。

nanocode 的 `--trace` 把事件写成 JSONL，可以完整回放一次任务，这就是审计和回放能力的雏形。

## 六、合规

| 类别 | 内容 | 何时需要 |
|---|---|---|
| 安全认证 | SOC 2 Type II、ISO 27001、ISO 27701（隐私） | 向中大型企业销售前；L1 阶段启动，通常需要 6–12 个月 |
| 中国 | 网络安全等级保护（等保）、个人信息保护法、数据出境安全评估、生成式人工智能服务备案、算法备案 | 在中国提供服务前 |
| 欧盟 | GDPR、欧盟人工智能法案（按风险分级的义务） | 服务欧盟用户前 |
| 行业 | 医疗（如 HIPAA）、金融（各地金融监管对外包和数据的要求） | 进入这些行业时 |
| 公共部门 | 各国政府云安全认证 | 服务政府客户时 |

合规能力需要按区域配置：数据驻留、可用模型、内容安全规则、保留期、备案信息展示。

## 七、AI 治理

- **透明**：用户知道自己在和 AI 交互；Agent 的产出标明哪些是 AI 生成的；运行时身份（使用的模型）可查（nanocode issue #21 的教训）。
- **评测与发布**：模型、提示词、Agent 定义的变更必须通过质量和安全评测才能发布（见 09）。
- **人类监督**：高风险操作有人审批；组织可以查看 Agent 的运行记录和决策依据。
- **可追责**：每个操作都能追溯到发起人、Agent 定义版本、模型版本、命中的策略。
- **负责任的使用政策**：明确禁止的用途；违规检测和处置流程。

## 八、安全工作的阶段安排

| 阶段 | 必须完成 |
|---|---|
| L1 内测前 | 威胁建模；执行环境隔离和出口控制；凭证不进执行环境；跨租户测试；审计日志 |
| L1 正式上线前 | 第三方渗透测试；提示词注入红队评测；数据防泄漏基础规则；事件响应流程；SOC 2 审计启动 |
| L2 前 | SOC 2 Type II、ISO 27001 认证；漏洞奖励计划；工具市场安全审核流程；专职安全团队和 7×24 安全值班 |
| L3 | 各主要市场的监管合规团队；大规模内容安全和反滥用运营；国家级攻击者的防御能力 |
