# 11 实施路线图

## 一、总体节奏

```
第 0–2 月     第 2–6 月          第 6–12 月           第 2–3 年                 第 3 年起
┌────────┐  ┌──────────────┐  ┌────────────────┐  ┌────────────────────┐  ┌──────────────────┐
│ P0 准备  │─▶│ P1 平台 MVP    │─▶│ P2 企业版正式上线 │─▶│ P3 规模化（L2）       │─▶│ P4 全球通用（L3）   │
│ 决策、团队│  │ 一家企业内部试点 │  │ 多家企业、10 万用户│  │ 千万用户、多区域、自建 │  │ 公司级战略          │
└────────┘  └──────────────┘  └────────────────┘  └────────────────────┘  └──────────────────┘
```

每个阶段结束有一个**决策关口**：达到完成标准才进入下一阶段，没达到就延长当前阶段或调整方向。时间是在团队按计划到位的前提下的估算。

---

## 二、P0 准备（第 0–2 月）

**目标**：做完不可逆的关键决策，组建核心团队，建立评测基线。

| 工作 | 产出 |
|---|---|
| 确定首批场景 | 从 [01](01-vision-and-scope.md#五典型场景用于验证设计) 的场景中选 3–5 个作为 P1 目标，有明确的试点用户和成功标准 |
| 架构决策 | ADR-001 至 ADR-006 定稿：运行引擎、执行环境技术、云厂商、模型厂商、检索方案、单元划分 |
| 威胁建模 | 覆盖 [08](08-security-and-governance.md) 的威胁表，确定 P1 必须完成的安全措施 |
| 评测基线 | 首批场景的评测集（每个场景 30–50 个任务，带自动检查）；用现有模型测出基线成功率和成本 |
| 模型厂商 | 至少两家厂商的企业合同、数据处理协议、额度确认 |
| 团队 | 核心团队到位（见第七节） |
| 原型 | 用 nanocode 加 [第 12 章](../12-distributed-deployment.md) 的方案，在单一场景上做一个可用的原型，验证场景价值 |

**决策关口**：试点用户确认场景有价值；评测基线显示成功率有希望达到目标；预算批准。

## 三、P1 平台 MVP（第 2–6 月）

**目标**：在一家企业内部（或一个大部门）上线，1000 名左右用户日常使用。

### 范围

| 领域 | P1 要做的 | 推迟到以后 |
|---|---|---|
| 运行时 | 关系库实现的持久化运行（每步检查点）、Worker 池、取消、预算上限、子 Agent | 专用执行引擎、快速路径 |
| 执行 | E2 容器沙箱 + 预热池 + 出口白名单 + 凭证代理；设备端执行（桌面端或命令行，基于 nanocode） | E1、E3、E5 |
| 模型 | 模型网关：两家厂商、按组织限流和预算、故障切换、计量 | 自建推理、复杂路由 |
| 知识 | 3–5 个知识源连接器、带 ACL 的混合检索、引用来源 | 大规模增量同步优化 |
| 集成 | 5–10 个核心连接器（邮件、日历、网盘、IM、工单、代码托管）；代表用户的 OAuth；凭证保险库 | 工具市场、企业内网网关 |
| 安全 | SSO、RBAC、策略引擎（基础规则）、审批（网页 + IM）、审计日志、跨租户测试 | 数据防泄漏高级规则、BYOK |
| 入口 | 网页、一个 IM、设备端客户端 | 开放 API 正式版、浏览器插件 |
| 运维 | 单区域单元、托管服务、基础监控和告警、运行回放 | 多区域 |
| 质量 | 评测门禁、线上抽样、用户反馈收集 | 自动化失败分析 |

### 里程碑

| 时间 | 里程碑 |
|---|---|
| 第 3 月末 | 运行时、模型网关、执行沙箱打通；内部团队（20 人）开始使用 |
| 第 4 月末 | SSO、策略、审批、审计、3 个连接器完成；安全评审通过；试点扩大到 100 人 |
| 第 5 月末 | 知识检索带权限过滤上线；第三方渗透测试完成并修复高危问题 |
| 第 6 月末 | 1000 人试点；首批场景成功率达标 |

**决策关口**：
- 1000 名用户连续使用一个月，周活跃率 ≥ 40%；
- 首批场景评测成功率 ≥ 70%；
- 零跨租户、零越权事故；
- 单位成本在可接受范围（为 P2 定价提供依据）。

## 四、P2 企业版正式上线（第 6–12 月）

**目标**：对外销售，10–30 家企业客户，总计约 10 万用户。

| 领域 | 工作 |
|---|---|
| 多租户 | 多组织、工作空间、配额、多单元、专属单元 |
| 管理后台 | [10](10-delivery-and-business.md#二管理后台) 列出的模块 |
| 安全合规 | SCIM、BYOK、数据防泄漏、审计导出到 SIEM；SOC 2 Type I 完成、Type II 观察期开始；ISO 27001 启动；目标市场的备案 |
| 运行时 | 定时和事件触发、无人值守运行的策略、多 Agent 并行、快速路径 |
| 执行 | 浏览器执行环境（E4）；快照与休眠 |
| 集成 | 企业内网网关；20–30 个连接器；开放 API 和 SDK 正式版 |
| 交付 | 私有化部署的技术验证（一个试点客户） |
| 商业 | 定价、计量计费、合同模板、客户成功流程 |
| 质量 | 每个场景的评测集扩充到 100+ 任务；质量看板；失败分析流程 |
| 运维 | 7×24 值班、状态页、事故管理流程、区域级灾备演练 |

**决策关口**：
- 至少 10 家付费企业客户，续约意向良好；
- 可用性达到 99.5%；
- 毛利为正（按客户分层核算）；
- SOC 2 Type I 报告完成。

## 五、P3 规模化到 L2（第 2–3 年）

**目标**：千万级用户，多区域，单位经济模型健康。同时开启通用 Agent 产品线。

| 方向 | 关键工作 |
|---|---|
| 架构 | 专用持久化执行引擎；数据按组织分片；事件总线换成 Kafka 类；几十到上百个单元的自动化管理 |
| 执行 | 自建微虚拟机机群（E3）、快照恢复、超量分配；轻量执行（E1）；**设备端优先**策略全面推广 |
| 模型 | 自建推理集群承担大部分简单步骤；模型分级路由；预留算力合同；批处理 |
| 区域 | 至少 3 个区域（按目标市场）；数据驻留；区域级故障转移 |
| 产品 | 通用 Agent（面向个人）：免费 + 付费档位；工具市场；更多入口 |
| 安全 | SOC 2 Type II、ISO 27001；漏洞奖励计划；反滥用体系（实名或支付验证、风险评分、异常检测）；专职安全团队 |
| 组织 | 平台工程、SRE、安全、合规、反滥用、客户成功等专门团队 |

**关键里程碑**（按季度推进，此处只列关键节点）：

| 节点 | 标志 |
|---|---|
| 第 2 年第 1 季度 | 第二个区域上线；自建推理承担 30% 以上的调用 |
| 第 2 年第 2 季度 | 通用 Agent 公测；工具市场开放首批第三方连接器 |
| 第 2 年第 4 季度 | 100 万用户；微虚拟机机群替代大部分容器沙箱 |
| 第 3 年 | 1000 万用户；可用性 99.9%；SOC 2 Type II、ISO 27001 完成 |

**决策关口**：单位成本持续下降并低于定价的 40%；多区域可用性达标；反滥用损失可控。

## 六、P4 全球通用 Agent（L3，第 3 年起）

到这一档，问题已经超出工程范畴，主要是公司战略：

- **模型**：自研或深度定制模型，针对 Agent 负载优化效率（见 ADR-007）。
- **算力**：自建数据中心、长期芯片采购、GW 级电力规划，提前 2–3 年布局。
- **终端**：在手机、电脑上运行的小模型承担简单和隐私敏感的请求。
- **全球运营**：几十个区域、每个主要市场的合规和公共政策团队、大规模内容安全和反滥用运营。
- **组织**：数千人规模，工程只是其中一部分。

是否走到这一档，取决于 P3 的市场结果和融资能力，不应提前为它做架构上的过度设计。P1–P3 的架构原则（循环与执行分离、步骤级持久化、单元化、模型网关、策略引擎）在 L3 仍然成立，变化的主要是每个组件的实现规模。

## 七、团队配置

| 阶段 | 规模（估算） | 构成 |
|---|---|---|
| P0 | 5–8 人 | 技术负责人、Agent 运行时、基础设施、安全、产品、评测 |
| P1 | 15–25 人 | 运行时与模型网关（4–6）、执行环境（3–4）、知识与连接器（3–5）、安全与身份（2–3）、前端与客户端（3–4）、SRE（1–2）、评测与质量（2）、产品与设计（2） |
| P2 | 40–80 人 | 上述扩大 + 管理后台、计费、私有化交付、合规、客户成功、售前 |
| P3 | 150–400 人 | 按领域形成独立团队：运行时、执行平台、模型与推理、知识、集成生态、安全、合规、反滥用、SRE、数据、通用 Agent 产品线、企业产品线 |
| P4 | 数千人 | 公司级组织 |

关键岗位最好在 P0 就到位：**Agent 质量与评测负责人**（决定产品是否真的有用）、**安全负责人**（决定能否上线）、**基础设施负责人**（决定成本和稳定性）。

## 八、前 90 天详细计划

| 周 | 工作 | 交付物 |
|---|---|---|
| 1–2 | 访谈试点用户，选定 3 个首批场景；确定成功标准；团队启动 | 场景说明书（输入、期望输出、成功判断方法）；成功指标 |
| 1–4 | 为首批场景各建 30–50 个评测任务；用 2–3 个模型跑基线 | 评测集和基线报告（成功率、成本、步数、典型失败） |
| 2–4 | 架构决策：运行引擎、执行技术、云、模型厂商、检索方案 | ADR-001 至 ADR-006 定稿 |
| 2–5 | 威胁建模；确定 P1 安全基线 | 威胁模型文档；安全需求清单 |
| 3–6 | 基于 nanocode 和第 12 章方案的原型，在一个场景上让 20 名内部用户试用 | 原型；用户反馈；第一批线上失败案例 |
| 4–8 | 模型网关、持久化运行（关系库实现）、Worker 池 | 内部服务可用；崩溃恢复测试通过 |
| 5–10 | 执行沙箱（E2）+ 出口控制 + 凭证代理；沙箱逃逸和出口绕过测试 | 执行服务可用；安全测试报告 |
| 6–10 | SSO、RBAC、策略引擎基础规则、审批（网页）、审计日志 | 身份与策略可用 |
| 8–12 | 首批 3 个连接器；知识检索（带 ACL）的第一个知识源 | 连接器可用；检索评测报告 |
| 10–13 | 端到端集成；首批场景评测；内部 20 人试用扩大到 100 人 | 第 90 天评审：场景成功率、稳定性、安全测试结果、P1 剩余计划 |

**第 90 天评审要回答的问题**：首批场景的成功率是否接近目标？用户是否在没有催促的情况下持续使用？有没有无法解决的安全问题？成本是否在预期范围内？据此决定 P1 后半段的范围调整。

## 九、主要风险

| 风险 | 影响 | 可能性 | 应对 |
|---|---|---|---|
| Agent 成功率达不到可用水平 | 用户不持续使用，项目失败 | 中 | 从高价值、可验证的窄场景开始；评测驱动迭代；P0 就建评测基线 |
| 提示词注入导致数据泄露或误操作 | 严重的客户信任和法律问题 | 中 | 纵深防御（08）；默认审批；红队评测；先在内部试点 |
| 模型成本过高 | 毛利为负 | 高（L2） | 早期就做计量和单位成本分析；缓存、路由、上下文控制；用量挂钩的定价 |
| 模型厂商限流、故障、涨价、停服 | 服务不可用或成本突增 | 中 | 多厂商；模型网关可快速切换；评测保证切换后的质量 |
| 模型能力快速变化，架构过时 | 重复建设 | 中 | 架构不绑定特定模型能力；保持 Agent 循环简单（nanocode 的循环只有几百行） |
| 企业集成工作量超预期 | 交付延期 | 高 | 优先使用 MCP 生态的现成连接器；场景模板；企业自建连接器的开发工具 |
| 合规认证周期长 | 大客户无法采购 | 中 | P1 就启动认证准备；早期选择对认证要求较低的客户 |
| 滥用（L2 通用产品） | 成本损失、法律风险、声誉 | 高 | 免费档不提供或严格限制执行环境；实名或支付验证；异常检测 |
| 关键人才招聘困难 | 进度延误 | 中 | P0 优先招关键岗位；能买的托管服务先买 |

## 十、和 nanocode 的关系

nanocode 是理解这些设计的起点，但不是平台的代码基础：

- **可以直接复用**的是思路和部分模块：Agent 循环的结构、统一消息格式和厂商适配、工具抽象、权限与风险分级、上下文压缩、验证闭环、评测框架。
- **设备端客户端**可以基于 nanocode 演进：它本来就是"模型在云端、命令在本地"的形态，接入平台的模型网关、策略引擎和审计即可。
- **平台服务**应该作为独立的代码库开发（见 ADR-009），nanocode 核心保持标准库、保持简洁，继续作为学习项目和设备端执行的参考实现。
