# 09 可靠性与运维

## 一、服务等级目标（SLO）

| 指标 | 定义 | L1 | L2 | L3 |
|---|---|---|---|---|
| 平台可用性 | 会话 API 成功响应的比例（不含客户端错误） | 99.5% | 99.9% | 99.95%（核心对话） |
| 首字延迟 p95 | 用户发消息到收到第一个字 | < 5 秒 | < 3 秒 | < 1.5 秒 |
| 执行环境就绪 p95 | 请求到可执行命令 | < 10 秒 | < 2 秒 | < 500 毫秒（轻量执行） |
| 运行不丢失 | 因平台故障导致运行丢失进度超过一步的比例 | < 0.1% | < 0.01% | < 0.001% |
| 审批送达 | 审批请求在 10 秒内送达至少一个渠道 | 99% | 99.9% | 99.9% |
| 恢复点目标（RPO） | 区域级灾难时最多丢失的数据 | 15 分钟 | 1 分钟 | 秒级（关键数据） |
| 恢复时间目标（RTO） | 区域级灾难后恢复服务 | 4 小时 | 30 分钟 | 分钟级 |

**模型厂商的故障不计入平台可用性，但计入用户体验指标**。厂商故障时平台要做到：自动切换（如果 Agent 定义允许）、明确提示、运行进入等待而不是失败。

## 二、单元化与故障隔离

```
全局路由（组织 → 单元）
   │
   ├── 单元 1：完整的服务栈 + 独立数据库 + 独立执行池
   ├── 单元 2
   └── ……
```

- 每个单元服务固定的一组组织，单元之间不共享数据库和队列。
- 一个单元的故障（包括错误的发布、数据库故障、某个租户的异常负载）只影响这个单元的租户。
- 单元的规模有上限（例如几万到几十万用户），达到上限就新建单元，而不是继续放大单元。
- 组织可以在单元之间迁移（大客户独立、负载均衡），迁移流程要自动化并演练。
- 少数全局组件（身份、路由表、计费汇总）单独设计高可用，且故障时单元能降级运行（例如使用缓存的路由和策略）。

## 三、多区域容灾

| 档位 | 方案 |
|---|---|
| L1 | 单区域多可用区；数据库跨可用区主备；对象存储跨区域复制；有书面的区域级恢复流程并每年演练 |
| L2 | 每个区域内多可用区；关键数据跨区域异步复制到灾备区域（满足驻留要求的前提下，如同一国家内的两个区域）；单元级故障转移自动化 |
| L3 | 区域级故障时，用户自动切换到同一合规范围内的其他区域；核心对话能力在多区域同时可用 |

运行中的任务在区域故障时：已持久化的步骤在灾备区域可见，运行从最近的检查点恢复；执行环境需要从快照重建，如果快照尚未复制，运行进入等待并通知用户。

## 四、发布与变更

- **所有变更都可灰度、可回退**：代码、配置、策略、提示词、Agent 定义、模型版本都是变更。
- **按单元灰度**：先发布到内部单元，再到小比例的客户单元，观察指标后再扩大。
- **提示词和模型变更必须通过评测门禁**：这类变更不会让测试失败，但会让质量下降，只有评测能发现（见下文）。
- **向后兼容**：运行可能持续几天，新版本 Worker 必须能处理旧版本写入的步骤记录。
- **功能开关**：按组织、按用户开关新功能。
- **冻结期**：大客户的关键时期、节假日等可以冻结发布。

## 五、Agent 质量运营

传统服务的监控回答"服务是否正常"，Agent 平台还需要回答"Agent 是否做对了"。

| 手段 | 说明 |
|---|---|
| 离线评测集 | 每类场景（编程、数据分析、知识问答、办公自动化、浏览器操作）都有评测任务和自动检查，nanocode 的 `evals/agent_tasks` 就是这种结构 |
| 发布门禁 | 模型、提示词、工具、检索管线的变更必须在评测集上不退化（成功率、成本、步数、安全类任务） |
| 线上抽样评分 | 按比例抽取运行，用评分模型 + 人工抽检评估是否完成任务、是否有不当操作 |
| 用户信号 | 点赞点踩、重新生成、中途取消、审批被拒、用户手动修改 Agent 的产出 |
| 回放 | 任何一次运行都可以按步骤回放（上下文、模型输出、工具调用），用于排查（nanocode 的 trace + Web 调试面板的平台版） |
| 失败分析 | 定期按失败类型归类（理解错误、工具调用错误、检索不到、权限不足、厂商故障），找出改进优先级 |
| 质量看板 | 按场景、Agent 定义、模型、组织展示成功率、成本、步数、用户满意度的趋势 |

## 六、可观测性

| 类型 | 内容 |
|---|---|
| 指标 | 各组件的请求量、延迟、错误率；运行数（按状态）、排队长度、等待中的运行数；执行环境数量、启动耗时、资源使用；模型调用量、token、缓存命中率、各厂商错误率和限流次数；连接器调用成功率；成本（按组织、模型、组件） |
| 日志 | 结构化日志，带 `org_id`、`run_id`、`step`、`trace_id`；正文和参数脱敏 |
| 链路追踪 | 一次运行是一条链路，每个步骤（模型调用、工具调用、等待）是一个跨度，能看清时间花在哪里 |
| 告警 | 基于 SLO 消耗速度告警，而不是单个指标阈值；按严重程度分级通知 |

## 七、事故管理

- **值班**：L1 工作时间值班 + 非工作时间紧急响应；L2 起 7×24 分组值班（平台、执行环境、模型层、安全）。
- **分级**：按影响范围（单个组织 / 单元 / 区域 / 全局）和影响程度分级，决定响应时间和通知范围。
- **预案**：每类常见故障都有写好的处理步骤，例如：
  - 模型厂商故障或限流：切换路由、暂停低优先级任务、对外公告
  - 执行环境资源耗尽：开启排队、扩容、暂停免费用户的执行环境
  - 单元数据库故障：主备切换、只读降级
  - 发现跨租户数据泄露：立即隔离、取证、按法规时限通知客户和监管机构
  - 发现大规模滥用：封禁、收紧出口策略、提高验证要求
- **复盘**：不追责的复盘，产出改进项并跟踪完成。
- **状态页**：对客户公开的服务状态和事故通告。

## 八、成本运营（FinOps）

- **单位成本看板**：每次运行、每个活跃用户、每个组织的成本（模型 + 执行 + 存储 + 连接器），和收入对比。
- **预算与告警**：按组织、按团队、按 Agent 定义设置预算，接近时告警，超过时按策略限制。
- **异常检测**：单个运行、单个组织的成本突增（例如 Agent 陷入循环），自动暂停并通知。
- **定期优化**：分析成本最高的 Agent 定义和步骤类型，针对性优化（缓存、路由、上下文控制）。
- **容量规划**：按增长预测提前采购（预留实例、模型厂商的预留算力、GPU），L2 起以季度为单位规划，L3 以年为单位。
