# 02 总体架构

## 一、设计原则

1. **Agent 循环和执行环境分离**：Agent 的"思考"（调用模型、决定下一步）跑在共享的、无状态的 Agent Worker 上；"动手"（执行代码、操作浏览器）才分配隔离的执行环境。通用 Agent 的大部分任务根本不需要执行环境。见 ADR-001。
2. **以步骤为单位持久化**：每一次模型调用、每一次工具调用都是一个可持久化、可重放的步骤。任何组件故障，任务都从最近一步继续，而不是从头再来。见 ADR-002。
3. **安全靠架构，不靠模型自觉**：权限、隔离、审批、出口控制都在模型之外强制执行。模型被提示词注入后能做的事，不会超过发起人被授权做的事。
4. **单元化**：服务按单元部署，每个单元完整、独立，服务一部分租户。扩容就是加单元，故障只影响一个单元。见 ADR-003。
5. **模型可替换**：所有模型调用经过模型网关，业务代码不直接依赖某一家厂商。
6. **一切可计量**：每个步骤的 token、执行时长、存储都记到组织、用户、Agent、任务上，成本可以分摊、限制和预测。
7. **核心事件化**：组件之间通过事件总线解耦，界面、审计、计费、监控都是事件的订阅者。这和 nanocode 的 `events.py` 是同一个思路的放大版。

## 三、组件职责

| 组件 | 职责 | 状态 | 详细设计 |
|---|---|---|---|
| **接入网关** | TLS 终止、认证令牌校验、按租户 / IP 限流、WAF、长连接管理、按租户路由到所在单元 | 无状态 | 09 |
| **控制面** | 组织、工作空间、成员、角色；SSO / SCIM；Agent 定义；策略；配额；单元分配；管理后台 API | 有状态（全局库，读多写少，可缓存） | 08、10 |
| **会话 API** | 创建会话、发消息、取消、查询历史、订阅事件流、提交审批结果 | 无状态 | 03 |
| **编排服务** | 持久化运行引擎：把一次运行拆成步骤，调度、检查点、重试、超时、等待（审批、定时）、取消、子任务编排 | 状态在运行状态存储 | 03 |
| **Agent Worker** | 执行"一步"：组装上下文 → 调模型 → 解析工具调用 → 交给工具运行时 → 返回结果。不保存任何跨步骤状态 | 无状态 | 03 |
| **工具运行时** | 工具注册、参数校验、策略检查（是否允许、是否需要审批）、调用分发、结果截断与脱敏 | 无状态 | 03、07 |
| **执行服务** | 管理执行环境池：代码沙箱、浏览器、桌面；创建、快照、恢复、回收；资源调度 | 有状态（沙箱本身） | 04 |
| **模型网关** | 统一的模型调用接口：路由、限流、排队、重试、切换厂商、缓存、计量、内容安全检查 | 无状态（计数器在缓存） | 05 |
| **推理集群** | L2 起自建：部署开源或自研模型，承担大量的简单步骤以降低成本 | 有状态（模型权重、KV 缓存） | 05 |
| **知识服务** | 文档接入、切分、索引（全文 + 向量）、按权限过滤的检索、引用溯源 | 有状态（索引） | 06 |
| **连接器中心** | 托管连接器（MCP 服务器）、OAuth 授权、调用外部 API、外部系统限流 | 无状态 + 凭证 | 07 |
| **凭证保险库** | 保存 OAuth 令牌、API Key、数据库密码；按需签发短期凭证；Agent 和沙箱永远拿不到长期凭证 | 有状态（加密） | 07、08 |
| **策略引擎** | 统一回答"这个主体能不能对这个资源做这个动作、需不需要审批"。nanocode `permissions.py` 的平台版 | 无状态（策略缓存） | 08 |
| **事件总线** | 可靠、有序（按运行）、可回放的事件流 | 有状态 | 03、09 |
| **审计服务** | 只追加的审计日志，支持导出到客户的 SIEM | 有状态 | 08 |
| **计量计费** | 汇总 token、执行时长、存储、连接器调用；配额扣减；账单 | 有状态 | 10 |
| **记忆服务** | 用户和组织级记忆的提取、确认、存储、检索、遗忘 | 有状态 | 06 |
| **评测与质量** | 离线评测、线上抽样评分、发布门禁、回归分析 | 有状态 | 09 |
| **可观测性平台** | 指标、日志、链路追踪、Agent 运行回放 | 有状态 | 09 |

## 四、一次运行的完整流程

以场景 S4（每天早上汇总工单、告警和销售数据，发到群里）为例，说明组件之间如何协作：

```
定时触发器          编排服务            Agent Worker         工具运行时 / 策略引擎         外部
    │ 08:00 创建运行    │                     │                      │
    ├──────────────▶ │ 写入运行记录          │                      │
    │                 │ 调度步骤 1 ────────▶ │ 组装上下文（Agent 定义、
    │                 │                     │ 记忆、可用工具）
    │                 │                     │ 调模型网关 ─────────────────────────────▶ 模型
    │                 │                     │ ◀─ 要调用：工单查询、告警查询、销售查询（并行）
    │                 │ ◀─ 步骤 1 结果+检查点 │
    │                 │ 调度步骤 2a/2b/2c ──▶ │ ──── 每个工具调用 ─▶ │ 策略：只读，允许
    │                 │                     │                      │ 凭证保险库签发短期令牌
    │                 │                     │                      │ 连接器中心调用 ──────▶ 工单/监控/CRM
    │                 │ ◀─ 三个结果+检查点    │ ◀──────────────────── │
    │                 │ 调度步骤 3 ────────▶ │ 调模型：写汇总 ───────────────────────────▶ 模型
    │                 │ ◀─ 要调用：发群消息   │
    │                 │ 调度步骤 4 ────────▶ │ ──── 发消息 ────────▶ │ 策略：对外发送，命中
    │                 │                     │                      │ "群消息需检查敏感数据"
    │                 │                     │                      │ 数据防泄漏扫描通过 → 允许
    │                 │                     │                      │ 连接器中心调用 ──────▶ IM
    │                 │ ◀─ 完成              │
    │                 │ 写运行结果；发出事件 ─▶ 事件总线 → 审计、计量、通知
```

如果第 4 步策略结果是"需要审批"，编排服务把运行置为**等待审批**，不占用任何 Worker 或执行环境；审批人在 IM 或网页上点同意后，编排服务继续调度第 4 步。

如果任何一步执行时 Worker 崩溃，编排服务在超时后把这一步重新调度到另一个 Worker；已经完成的步骤直接用检查点里的结果，不重复调用模型和工具。有副作用的工具调用带**幂等键**，保证重试不会发两次消息，见 [03 Agent 运行时](03-agent-runtime.md#五工具调用的幂等与副作用)。

## 五、部署拓扑与演进

### L1：一个区域，一到几个单元

```
一个区域
├── 全局控制面（主备）
├── 单元 1 ── 编排 · Worker · 网关 · 执行池 · 知识 · 数据库（主备）· 缓存 · 对象存储
└── 单元 2 ……（按租户数量和隔离需求增加；大客户可独占单元）
外部模型厂商（2–3 家）
```

- 托管云服务为主：托管 Kubernetes、托管关系库、托管缓存、托管对象存储。
- 运行状态存储可以直接用关系库（运行表 + 步骤表），事件总线可以用托管的消息队列。
- 执行环境用 gVisor 或 Kata 的 Kubernetes Pod，配合预热池。
- 团队规模小，**能买的都买**，把精力放在 Agent 质量、安全和企业集成上。

### L2：多区域，几十到上百个单元

```
全局层：全局身份与账号 · 全局控制面 · 单元路由表 · 全局计费
区域 A（如华东）  区域 B（如欧洲）  区域 C（如北美） ……
├── 区域控制面（策略、配额缓存）
├── 单元 1 … 单元 N（每个服务几万到几十万用户）
├── 区域共享：推理集群 · 执行服务的机器池 · 数据仓库
└── 跨区域：仅元数据和计费汇总；用户内容不出区域
```

和 L1 相比的变化：

| 方面 | L1 | L2 |
|---|---|---|
| 运行引擎 | 关系库 + 队列 | 专用持久化执行引擎（自研或 Temporal 类），按单元分片 |
| 关系库 | 单库主备 | 按组织分片；消息正文移到对象存储 / 宽表 |
| 事件总线 | 托管消息队列 | Kafka 类，按单元分区，分级保留 |
| 执行环境 | 容器沙箱 + 预热池 | 自建微虚拟机机群（Firecracker 类），快照恢复，休眠，超量分配 |
| 模型 | 外部厂商 | 外部厂商（预留算力合同）+ 自建推理集群承担大部分简单步骤 |
| 优先执行位置 | 云端 | **能在用户设备上执行的放在设备上**（桌面端、IDE、命令行），见 ADR-004 |
| 运维 | 托管服务 + 小 SRE 团队 | 平台工程团队，7×24 值班，自动化发布和故障转移 |

### L3：全球，自建基础设施

- 几十个区域，接入网关下沉到边缘节点，就近接入。
- **执行分级**（见 [04 执行与沙箱](04-execution-sandbox.md)）：大部分请求只需要模型和轻量工具；需要执行代码的优先用 WebAssembly 级别的轻量隔离；只有少数请求分配微虚拟机；能在设备上执行的在设备上执行。
- 推理以自研或深度定制的模型为主，自建数据中心和推理芯片集群，电力按 GW（吉瓦）级规划。
- 控制面和数据层全部为全球规模重新设计：全局唯一 ID、跨区域一致性只用在账号和计费等少数地方。
- 各国合规、内容安全、未成年人保护、选举等特殊时期的策略，都需要按区域独立配置和运营。

## 六、关键接口（概要）

外部 API 以"运行"为核心资源，所有写操作支持幂等键：

```
POST   /v1/sessions                              创建会话（指定 Agent 定义）
POST   /v1/sessions/{sid}/runs                   发起一次运行（用户消息、附件、预算上限）
GET    /v1/runs/{rid}                            运行状态、结果、用量
GET    /v1/runs/{rid}/events?after={seq}         事件流（SSE），支持断点续传
POST   /v1/runs/{rid}/cancel                     取消
POST   /v1/approvals/{aid}                       提交审批（同意 / 拒绝 / 修改参数后同意）
GET    /v1/runs/{rid}/artifacts                  运行产出的制品
POST   /v1/agents                                注册 Agent 定义（工具、模型、策略、知识范围）
POST   /v1/triggers                              创建定时 / 事件触发
```

内部的编排服务与 Agent Worker 之间、Worker 与工具运行时之间的接口见 [03 Agent 运行时](03-agent-runtime.md)。

## 七、技术选型原则

不在这里锁定具体产品，按以下原则在每一档做选择，选择结果记录到 [12 架构决策记录](12-adr.md)：

- **L1 优先托管服务**，团队精力放在差异化能力上；L2 对成本占比高的部分（执行环境、推理、存储）逐步自建。
- **有状态的组件尽量少**，每一个都要明确：数据怎么分片、怎么备份、怎么跨区域、坏了怎么恢复。
- **避免把核心状态放在单一厂商的专有服务里**，以便满足私有化部署（客户机房里没有公有云服务）。
- **私有化部署要能用同一套代码**：所有依赖的外部服务都要有可替换的开源实现（对象存储、消息队列、关系库、向量检索）。
