# 07 集成与工具生态

企业 Agent 的价值大部分来自"能操作企业已有的系统"。本篇讨论连接器怎么接入、Agent 以谁的身份操作外部系统、凭证怎么保管，以及工具生态怎么开放。

## 一、工具的分类

| 类别 | 例子 | 提供方 |
|---|---|---|
| 平台内置工具 | 读写制品、检索知识、记忆、待办、子 Agent、执行代码、浏览网页 | 平台 |
| 平台认证连接器 | 邮件、日历、网盘、文档、IM、工单、CRM、代码托管、常见数据库 | 平台维护 |
| 企业自建连接器 | 企业内部系统的 API | 企业开发，部署在平台托管或企业内网 |
| 第三方连接器（L2 起） | 工具市场里的连接器 | 第三方开发者，经过审核 |

## 二、协议：以 MCP 为标准

工具和连接器统一使用 MCP（Model Context Protocol）描述和调用（nanocode 的 `mcp.py` 已经实现了客户端）。理由见 ADR-008：

- 生态中已有大量现成的 MCP 服务器；
- 企业可以用同一套协议开发内部连接器；
- 平台只需要实现一个适配层。

平台在 MCP 之上增加：

| 增加的内容 | 说明 |
|---|---|
| 副作用等级 | 每个工具声明 `只读` / `可逆写入` / `不可逆写入` / `对外发送` / `涉及资金`，供策略引擎和审批使用 |
| 幂等支持 | 有副作用的工具接受幂等键（见 03） |
| 权限范围 | 工具需要的 OAuth 范围，授权时展示给用户 |
| 速率信息 | 外部系统的限流规则，连接器中心据此排队 |
| 数据分类 | 工具返回的数据敏感级别，供数据防泄漏使用 |

## 三、连接器的部署方式

| 方式 | 适用 | 说明 |
|---|---|---|
| 平台托管（远程 MCP 服务） | 公有 SaaS 系统（邮件、网盘、IM） | 平台运行连接器，多租户共享，按组织隔离调用和凭证 |
| 企业内网网关 | 企业内部系统、私有数据库 | 企业在内网部署一个网关，主动向平台建立出站连接（无需开放入站端口），平台通过它调用内网连接器 |
| 设备端 | 本地文件、本地应用 | 通过桌面端客户端执行（见 04 的设备端执行） |
| 执行环境内 | 用户自带的脚本型工具 | 在执行环境里运行，受隔离约束 |

**不允许**：用户在平台托管环境里任意启动自定义 MCP 服务器进程（等于任意代码执行）。自定义连接器要么跑在执行环境里，要么部署在企业自己的网关后面，要么经过审核进入工具市场。nanocode 的 `trust.py` 把项目里的 `mcpServers` 视为敏感配置，也是同样的原因。

## 四、身份：Agent 以谁的身份操作

这是企业集成里最重要、也最容易出问题的设计。

| 模式 | 做法 | 适用 |
|---|---|---|
| **代表用户（推荐默认）** | 用户通过 OAuth 授权平台以自己的身份访问外部系统；Agent 的操作权限 = 用户在外部系统里的权限 ∩ Agent 定义允许的范围 | 绝大多数交互式场景 |
| 服务账号 | 组织管理员配置一个服务账号，Agent 以它的身份操作 | 定时汇总、系统间自动化；服务账号权限必须最小化，操作记录中同时记录"是谁的触发器" |
| Agent 身份（L2 起） | 每个 Agent 定义有自己的身份（类似员工账号），在外部系统里有独立的权限和审计记录 | 长期运行的"数字员工"类 Agent |

规则：

- Agent 的权限**永远不超过**它所代表的主体的权限。
- 权限取三者交集：用户（或服务账号）的权限、Agent 定义允许的工具和范围、组织策略。
- 外部系统里的操作记录要能追溯到平台的运行 ID（通过请求头或备注写入）。

## 五、凭证保险库

| 方面 | 设计 |
|---|---|
| 存储 | OAuth 刷新令牌、API Key、数据库密码，用组织级密钥加密；支持客户自管密钥 |
| 使用 | 调用时按（组织、用户、连接器、运行）签发短期访问令牌；Agent Worker、执行环境、模型都不接触长期凭证 |
| 范围 | 签发的令牌只包含这次调用需要的范围 |
| 生命周期 | 用户可以随时撤销授权；成员离职时（SCIM 同步）自动撤销其所有授权和触发器 |
| 审计 | 每次签发、使用、撤销都记录 |

## 六、连接器中心的运维

- **外部系统限流**：按（组织、外部系统）排队，遵守外部系统的配额，避免一个组织的大批量任务把整个组织的外部 API 配额用光。
- **错误处理**：区分可重试错误（网络、限流）和不可重试错误（权限不足、参数错误），后者作为工具错误结果交给模型，让它调整做法或告诉用户。
- **连接器版本**：连接器升级时保持工具名和参数向后兼容；不兼容的变更发新工具名，旧的逐步下线。
- **健康监控**：每个连接器的成功率、延迟、外部系统故障，故障时在 Agent 的工具列表中暂时隐藏或标注不可用。

## 七、工具市场（L2 起）

| 环节 | 要求 |
|---|---|
| 准入 | 开发者实名；连接器声明所需权限、副作用等级、数据去向 |
| 审核 | 自动扫描（依赖漏洞、可疑网络行为）+ 人工审核高权限连接器 |
| 运行 | 第三方连接器在隔离环境里运行，出口受限 |
| 安装 | 组织管理员决定哪些第三方连接器可以被成员使用 |
| 监控 | 异常行为检测（突然大量读取数据、向未声明的地址发送数据），可一键下架 |
| 商业 | 收入分成、按调用计费（可选） |

## 八、入口集成

Agent 也要出现在用户已经在用的地方：

- **IM 机器人**：企业微信、钉钉、飞书、Slack、Teams。在群里@Agent 发起运行，审批卡片直接在 IM 里处理。
- **IDE 和命令行**：编程场景，使用设备端执行（nanocode 的形态）。
- **浏览器插件**：在当前网页上下文中使用 Agent。
- **开放 API 和 SDK**：业务系统把 Agent 嵌入自己的流程。
- **邮件**：把邮件转发给 Agent 处理。

## 九、扩展的打包与分发

除了连接器，用户和组织还会扩展 Agent 的行为。nanocode 里已经有这些扩展的雏形：技能（`skills/`）、自定义斜杠命令（`commands/`）、hooks、MCP 服务器、项目记忆（`NANOCODE.md`）。平台需要让它们可以打包、版本化、分发和管控。

### 扩展的种类

| 种类 | 内容 | 会不会执行代码 | nanocode 对应 |
|---|---|---|---|
| 技能 | 一份说明 + 可选的脚本和模板，Agent 在需要时加载 | 说明本身不会；附带的脚本会（在执行环境或本机里） | `skills/` |
| 命令 | 预设的提示词模板，用户用 `/名称` 调用 | 不会 | `commands/` |
| 子 Agent 定义 | 一个专门用途的 Agent（提示词、工具子集、模型） | 不会（它调用的工具会） | `task` 工具 |
| hooks | 在工具调用前后、会话开始结束时运行的程序 | **会** | `hooks.py` |
| MCP 服务器 | 一组工具 | **会** | `mcp.py` |
| 插件 | 把以上几种打包在一起，作为一个单元安装 | 取决于内容 | — |

### 作用范围与优先级

```
平台托管（平台策略，不可覆盖）
  → 组织（管理员发布，可设为强制安装或可选）
    → 工作空间 / 项目（随代码仓库或工作空间配置）
      → 用户（个人安装）
```

和配置的信任规则一致（nanocode `trust.py`）：来自项目（代码仓库）的扩展，如果会执行代码（hooks、MCP 服务器、技能脚本），首次使用前必须由用户或组织策略批准；内容变化后重新批准。

### 打包与版本

- 每个插件有清单：名称、版本、包含的扩展、需要的权限（会执行哪些程序、需要访问哪些网络地址、需要哪些连接器授权）、支持的终端（例如"需要本机执行"的插件在网页和移动端不可用）。
- 版本号遵循语义化版本；组织可以固定版本，或允许自动更新小版本。
- 发布时签名；安装和更新时校验签名。

### 分发渠道

| 渠道 | 说明 |
|---|---|
| 组织目录 | 组织内部发布的插件，管理员审核后成员可安装，可以设为强制安装 |
| 代码仓库 | 随仓库提供的项目级扩展，打开项目时按信任规则加载 |
| 平台市场（L2 起） | 第三方插件，准入和审核流程同第七节的工具市场 |

### 跨端一致

同一个插件在命令行、桌面应用、云端会话中行为一致：插件定义存在云端（组织目录或市场），各端按清单声明的能力决定能否加载。本机会话（14 的 M1）通过策略包同步组织强制安装的插件和禁止的插件。
