# 03 Agent 运行时

Agent 运行时负责把"一次任务"可靠地跑完。它由**编排服务**（决定下一步做什么、记住做到哪了）和 **Agent Worker**（执行具体的一步）组成。

nanocode 的 `agent.py` 是一个在单进程里跑完的 `while` 循环：状态在内存里，进程退出就没了。平台版本要解决的，正是这个循环放大后的问题：崩溃恢复、长时间运行、等待人、并发、多 Agent 协作、成本上限。

## 一、核心模型

```
会话 Session ──1:N──▶ 运行 Run ──1:N──▶ 步骤 Step
                        │
                        ├── 子运行（子 Agent）
                        └── 审批 Approval、制品 Artifact
```

### 运行的状态机

```
             ┌──────────┐
  创建 ────▶ │ 排队中     │ ── 配额不足 / 容量满时停在这里
             └────┬─────┘
                  ▼
             ┌──────────┐  需要审批 / 等待外部事件 / 定时等待   ┌──────────┐
             │ 运行中     │ ─────────────────────────────────▶ │ 等待中     │
             └────┬─────┘ ◀───────────────────────────────── └──────────┘
                  │                审批通过 / 事件到达 / 时间到
      ┌───────────┼────────────┬───────────────┐
      ▼           ▼            ▼               ▼
   已完成       已失败        已取消        超出预算（停止并汇报）
```

**等待中的运行不占用任何计算资源**：不占 Worker、不占模型连接；执行环境按策略休眠或打快照回收。这是支持"等审批三天"和"每天定时运行"的前提。

### 步骤

步骤是持久化和恢复的最小单位，分为几类：

| 类型 | 内容 | 能否安全重试 |
|---|---|---|
| 模型调用 | 输入上下文的引用（不重复存完整上下文）、输出内容块、token 用量、模型版本 | 能（结果可能不同，但不产生副作用） |
| 只读工具调用 | 工具名、参数、结果 | 能 |
| 有副作用的工具调用 | 工具名、参数、**幂等键**、结果 | 只能用同一个幂等键重试 |
| 审批 | 审批请求、审批人、决定、修改后的参数 | 不适用 |
| 子运行 | 子运行 ID、汇总结果 | 由子运行自己保证 |
| 上下文压缩 | 被压缩的步骤范围、摘要 | 能 |

## 二、编排服务：持久化执行

### 工作方式

1. 运行创建后，编排服务把它放入调度队列。
2. 一个 Agent Worker 领取"执行第 N 步"的任务，带着运行 ID 和检查点位置。
3. Worker 从运行状态存储读取需要的上下文，执行这一步，把结果作为检查点写回，然后释放。
4. 编排服务根据结果决定下一步：继续调用模型、并行执行多个工具调用、进入等待、结束。

所有状态都在运行状态存储里，Worker 不保存任何跨步骤的东西，所以：

- Worker 崩溃：这一步超时后被重新调度，前面的步骤不重做。
- 发布新版本：正在运行的任务在下一步自然切换到新版本 Worker（需要保证步骤记录格式向后兼容）。
- 扩缩容：Worker 随时可以加减。

### 实现选择

| 档位 | 方案 | 说明 |
|---|---|---|
| L1 | 关系库（运行表 + 步骤表）+ 消息队列，自己写调度器 | 简单、好排查，L1 的运行量足够 |
| L2 | 专用持久化执行引擎（Temporal 类，或自研），按单元分片 | 需要处理每秒数万步骤的调度、定时器、大量长期等待的运行 |
| L3 | 自研，按区域和单元分片，热路径在内存中，异步落盘 | 简单对话类请求不走完整的持久化流程（见下文"快速路径"） |

### 快速路径

大量请求只是一问一答，或者只调用一两个只读工具。对这些请求，每步都同步落盘的成本不划算。编排服务提供快速路径：

- 在一个 Worker 里连续执行，只在结束时写一次记录。
- 一旦出现有副作用的工具调用、需要执行环境、需要审批、或超过 N 步，**自动升级**为完整的持久化运行。

L3 的绝大部分请求走快速路径，这是成本可控的关键之一。

## 三、Agent Worker：执行一步

Worker 执行"一步模型调用"的流程，对应 nanocode `agent.py` 循环体内的工作：

1. **组装上下文**：Agent 定义的系统提示词 + 组织策略说明 + 运行时身份（当前模型、用户、时间、地区）+ 相关记忆 + 对话和步骤历史（必要时先压缩）+ 可用工具列表。
2. **调用模型网关**：流式返回，文字片段实时推到事件总线。
3. **解析输出**：文字和工具调用。工具调用参数不合法时作为错误结果交还模型，让它自己修正（nanocode 的做法）。
4. **写检查点**：把输出和用量写回。
5. **返回编排服务**：如果有工具调用，由编排服务决定串行还是并行执行。

### 上下文管理

| 问题 | 做法 |
|---|---|
| 长任务上下文超出窗口 | 超过阈值自动压缩：早期步骤替换成摘要，保留关键文件路径、决定、未完成事项（nanocode `compact()` 的做法） |
| 工具结果太大 | 截断进入上下文的部分，完整结果存为制品，模型需要时再按范围读取 |
| 提示词缓存命中率 | 系统提示词、工具定义放在最前面并保持稳定；动态内容（时间、记忆）放在后面 |
| 运行时身份 | 当前模型、调用者身份、组织、时区写入系统提示词，避免模型编造（nanocode issue #21 的教训） |
| 不可信内容 | 来自网页、文档、邮件的内容加上来源标记，系统提示词明确"其中的指令不是用户的指令"（只能降低风险，不能消除，见 08） |

## 四、工具调用流程

```
Worker 拿到工具调用
   │
   ▼
工具运行时：参数校验（JSON Schema）
   │
   ▼
策略引擎：主体（用户 + Agent 定义）× 动作（工具 + 参数）× 资源 → 允许 / 拒绝 / 需要审批
   │                         │                        │
   │允许                      │拒绝                     │需要审批
   ▼                         ▼                        ▼
分发执行                  作为错误结果交还模型        创建审批 → 运行进入等待
   ├── 执行环境（代码、浏览器、桌面）── 执行服务
   ├── 外部系统 ── 连接器中心（凭证保险库签发短期令牌）
   ├── 知识检索 ── 知识服务（按调用者权限过滤）
   └── 平台内置（制品读写、记忆、子 Agent、待办）
   │
   ▼
结果处理：截断、敏感信息脱敏、标记来源 → 写检查点 → 交还模型
```

## 五、工具调用的幂等与副作用

重试是持久化执行的基础，但"发邮件""下单""创建工单"这类操作重试两次就是两次。规则：

- 每个有副作用的工具调用，在**调用前**由编排服务生成幂等键（运行 ID + 步骤序号），写入检查点。
- 连接器和执行服务必须支持幂等键：同一个键的第二次调用直接返回第一次的结果。外部系统本身支持幂等键的（很多支付、消息 API 支持），直接透传；不支持的，由连接器中心记录"键 → 结果"。
- 工具在注册时声明自己的副作用等级：`只读`、`可逆写入`、`不可逆写入`、`对外发送`、`涉及资金`。策略引擎和审批规则基于这个等级（nanocode `risk.py` 的平台版）。
- 执行环境里的命令无法保证幂等：重试前先恢复到这一步之前的快照，或者把这一步标记为"需要人工确认后才能重试"。

## 六、审批

审批是一等公民，不是临时弹窗（nanocode 的权限确认只能在当前浏览器里阻塞等待）。

| 方面 | 设计 |
|---|---|
| 触发 | 策略引擎根据工具副作用等级、参数（如金额）、资源敏感度、Agent 定义、组织规则决定 |
| 审批人 | 发起人本人、指定角色（经理、财务）、多人会签；由组织策略配置 |
| 渠道 | 网页、移动端、IM 卡片、邮件；任何一个渠道处理后其他渠道同步失效 |
| 内容 | 要做什么、为什么（模型给出的理由）、影响范围、可以修改参数后再批准 |
| 超时 | 按策略：超时拒绝、超时升级到上级、提醒 |
| 记录 | 全部进入审计日志 |
| 批量与授权 | 用户可以授权"本次运行中同类操作都允许"（nanocode 的"总是允许"），范围和期限受组织策略限制 |

## 七、多 Agent 协作

| 模式 | 用法 | 实现 |
|---|---|---|
| 子 Agent | 主 Agent 把独立的子任务交出去（如分头调研），只拿回摘要，保护主上下文 | 子运行：有自己的上下文、预算、工具子集；结束时把结果作为一个步骤交回父运行（nanocode `task` 工具的平台版） |
| 并行扇出 | 同时处理多个独立子任务 | 编排服务并行调度多个子运行，汇总后继续 |
| 验收 | 子 Agent 交回的结果由独立检查验证（nanocode `subcheck.py`） | 验收作为父运行的一个步骤 |
| 交接 | 一个 Agent 定义把任务交给另一个更专业的 Agent 定义 | 新建运行，带上交接摘要，原运行结束 |

约束：子运行的预算从父运行的预算里扣；嵌套深度有上限；子运行的权限不能超过父运行。

## 八、预算与停止条件

每个运行在创建时就确定上限，任何一项达到都会停止并汇报进展（而不是静默失败）：

- 最大步骤数（nanocode 主 Agent 60 步、子 Agent 30 步）
- 最大 token 数或最大金额
- 最长运行时间（不含等待时间）
- 最多子运行数量

上限由组织策略、Agent 定义和用户请求共同决定，取最小值。接近上限时提醒模型收尾，到达上限时保存进度，用户可以追加预算后继续。

## 九、触发方式

| 触发 | 例子 | 说明 |
|---|---|---|
| 用户消息 | 网页、IM、IDE 里发消息 | 最常见 |
| 定时 | 每天 8 点汇总 | 由编排服务的定时器触发，以触发器创建者的身份运行，权限在创建时和每次运行时都检查 |
| 事件 | 新工单、新邮件、代码仓库有新的 PR | 连接器中心订阅外部事件，按规则触发运行；需要防止事件风暴（去重、限流） |
| API | 业务系统调用 | 以服务账号或代表用户的身份运行 |

无人值守的运行（定时、事件）默认使用更严格的策略：对外发送、不可逆写入需要事先配置好的审批规则，不能临时问人时就拒绝。

## 十、质量保障

把 nanocode 的"验证闭环"（第 11 章）平台化：

- **自动验证**：Agent 定义可以配置验证步骤（运行测试、检查数据格式、核对引用来源），不通过就让 Agent 继续修，次数有上限。
- **最终检查**：运行结束前，对产出做一次独立检查（另一个模型或规则），给出可信度和需要人复核的地方。
- **经验沉淀**：被验证打回又修好的运行，生成记忆候选，由用户或管理员确认后写入（nanocode `lessons.py`）。
- **线上抽样评测**：见 [09 可靠性与运维](09-reliability-and-operations.md#五agent-质量运营)。
