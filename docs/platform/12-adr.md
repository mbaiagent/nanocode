# 12 架构决策记录

每条记录说明：背景、决策、考虑过的其他方案、后果，以及**什么情况下要重新评估**。新的重大决策按同样格式追加，已有决策被推翻时不删除，标记为"已被 ADR-xxx 取代"。

状态说明：**提议**（待 P0 评审）、**采纳**、**已取代**。本文档中的决策目前都是**提议**状态，需要在 P0 阶段由架构评审确认。

## ADR-001 Agent 循环与执行环境分离

- **状态**：提议
- **背景**：nanocode 把 Agent 循环和命令执行放在同一个进程里。[第 12 章](../12-distributed-deployment.md) 为了快速上线，建议 L1 编程场景采用"一个会话一个沙箱，循环也在沙箱里"。但对通用和企业 Agent，大部分运行（检索、调用连接器、写文档）根本不需要执行环境，把循环放进沙箱会让每个运行都占用一个沙箱。
- **决策**：Agent 循环运行在共享、无状态的 Agent Worker 上；只有工具调用需要时才分配执行环境，工具调用通过执行服务的接口发送到执行环境。
- **其他方案**：
  - 循环在沙箱内（第 12 章方案 A）：改动最小，但资源利用率低，且沙箱内需要能访问模型网关，增加了攻击面。
- **后果**：
  - 好处：大部分运行不需要执行环境；执行环境可以按需分配、休眠、回收；Worker 和执行环境可以分别扩缩容。
  - 代价：工具调用多了一次网络往返；工具上下文（当前目录、环境变量）要由执行服务维护。
  - 第 12 章的方案 A 可以作为 P0 原型使用，P1 起迁移到本方案。
- **重新评估**：如果主要场景变成长时间、高频命令执行的编程任务，且网络往返成为瓶颈，可以对这类 Agent 定义采用"循环靠近执行环境"的部署方式。

## ADR-002 以步骤为单位的持久化执行

- **状态**：提议
- **背景**：Agent 运行可能持续几分钟到几天，期间会遇到机器故障、发布、等待审批。nanocode 在整轮结束后才保存，中途故障会丢失整轮。
- **决策**：每个模型调用和工具调用都是一个持久化的步骤；运行的状态完全存储在运行状态存储中；任何 Worker 都可以从最近的检查点继续。有副作用的工具调用使用幂等键。L1 用关系库实现，L2 起使用专用的持久化执行引擎。
- **其他方案**：
  - 整轮保存：简单，但故障时损失大，无法支持长时间等待。
  - 一开始就用专用执行引擎：能力强，但 L1 的复杂度和运维成本过高。
- **后果**：每一步多一次存储写入（用快速路径缓解简单请求的开销）；步骤记录的格式需要长期向后兼容。
- **重新评估**：L1 运行量增长到关系库调度成为瓶颈时（预计 P2 后期），迁移到专用引擎。

## ADR-003 单元化架构

- **状态**：提议
- **背景**：多租户平台中，一个租户的异常负载、一次错误的发布、一个数据库故障，都可能影响所有客户。大客户还会要求独立部署。
- **决策**：服务按单元部署，每个单元是完整的服务栈，服务一组固定的组织；全局层只保留身份、路由、计费汇总等少数组件。
- **其他方案**：所有租户共享一套大集群，按服务横向扩展。初期更简单，但故障影响面大，很难提供专属部署。
- **后果**：需要单元管理的自动化（创建、发布、迁移组织）；跨单元的功能（跨组织协作）需要专门设计。
- **重新评估**：如果出现大量跨组织协作的需求。

## ADR-004 执行位置：设备优先，云端分级

- **状态**：已被 ADR-011 修订（云端分级部分仍然有效）
- **背景**：执行环境是除模型外最大的成本。L2 估算中，如果所有执行都在云端容器里，需要上万到数万 vCPU。编程和本地文件类任务的数据本来就在用户设备上。
- **决策**：能在用户设备上执行、且用户在线的，优先在设备上执行；云端执行按需求分级（E1 轻量计算 → E2 容器 → E3 微虚拟机 → E4 浏览器 → E5 桌面），默认分配满足需求的最低级别。
- **其他方案**：全部云端执行。体验一致、便于管控，但成本高，且需要把用户的本地数据上传。
- **后果**：需要桌面端、IDE、命令行客户端；设备端执行的安全依赖客户端和服务端策略的配合；企业需要设备管理策略。
- **重新评估**：如果目标用户主要使用移动设备或浏览器（没有可执行的本地环境）。

## ADR-005 模型网关是唯一出口，凭证不进入 Agent 和执行环境

- **状态**：提议
- **背景**：模型厂商 API Key 和外部系统凭证一旦进入 Agent 的上下文或执行环境，被提示词注入的模型就可能把它们发送出去。nanocode 的进程直接持有 API Key。
- **决策**：所有模型调用经过模型网关，厂商 Key 只存在于网关；所有外部系统调用通过连接器中心或出口代理，由凭证保险库签发短期令牌并在出站时注入。Agent Worker、执行环境、模型上下文中都不出现长期凭证。
- **其他方案**：调用方直连厂商，各自持有 Key。简单，但无法统一限流、计量、切换，且泄露面大。
- **后果**：网关成为关键路径，必须高可用、低延迟；需要支持各厂商的流式协议和特有字段。
- **重新评估**：不预期重新评估，这是安全底线。

## ADR-006 知识检索在索引时携带权限，检索时按调用者过滤

- **状态**：提议
- **背景**：企业知识检索最大的风险是 Agent 返回发起人无权查看的内容。
- **决策**：每个索引块携带源系统的访问控制信息（映射为平台的用户和组）；检索时用调用者身份过滤；权限变更的同步优先于内容同步；高敏感知识源在返回前再向源系统实时校验。
- **其他方案**：
  - 只做检索后实时校验：最准确，但慢，且受源系统 API 限流影响。
  - 按知识源整体授权（有权访问知识源的人能检索全部内容）：简单，但会扩大权限。
- **后果**：连接器必须能读取源系统的权限信息；需要同步组织架构（SCIM）；权限同步延迟就是泄露窗口，需要监控。
- **重新评估**：如果某些源系统无法提供权限信息，对这些源采用"仅授权者本人可见"。

## ADR-007 L3 阶段自研模型与推理基础设施

- **状态**：提议（P3 末期评审）
- **背景**：L3 的 token 量超过任何外部厂商能提供给单个客户的规模；模型效率直接决定毛利。
- **决策**：L1、L2 不训练基础模型，使用外部厂商并在 L2 自建开源模型推理；进入 L3 前评审是否自研模型和自建数据中心。
- **其他方案**：始终依赖外部厂商。在 L3 规模下可能无法获得足够算力，且毛利受制于人。
- **后果**：自研需要以年为单位的投入（研究团队、算力、数据），是公司级战略决定。
- **重新评估**：P3 末期，根据用户规模、外部厂商的供给和价格、融资情况决定。

## ADR-008 以 MCP 作为工具和连接器的标准协议

- **状态**：提议
- **背景**：企业需要接入大量外部系统；自定义工具协议意味着每个连接器都要自己开发。
- **决策**：工具和连接器统一使用 MCP；平台在其上扩展副作用等级、幂等键、权限范围、数据分类等元数据。
- **其他方案**：自定义工具协议。完全可控，但无法利用现有生态。
- **后果**：要跟进 MCP 规范的演进；平台扩展的元数据需要保持与标准兼容（作为可选字段）。
- **重新评估**：如果 MCP 规范的方向与平台需求严重偏离。

## ADR-009 平台服务与 nanocode 核心分离

- **状态**：提议
- **背景**：nanocode 是只用标准库的学习项目，简洁易读是它的核心价值。平台需要数据库驱动、消息队列客户端、Web 框架、云 SDK 等大量依赖。
- **决策**：平台服务作为独立代码库开发。nanocode 核心保持只用标准库，作为学习项目和设备端执行的参考实现；平台通过事件订阅者、存储后端接口、策略接口等少量扩展点复用 nanocode 的思路或模块。
- **其他方案**：在 nanocode 仓库里直接演进成平台。会让学习项目变得庞大复杂，失去教学价值。
- **后果**：两边的概念（消息格式、工具接口、事件类型）要保持对应关系，便于学习者从 nanocode 理解平台。
- **重新评估**：不预期重新评估。

## ADR-010 审批由策略引擎统一决定，作为运行状态的一部分

- **状态**：提议
- **背景**：nanocode 的权限确认在当前浏览器或终端里阻塞等待，最多等 10 分钟，页面关闭就按拒绝处理。企业场景需要多人审批、多渠道、长时间等待、无人值守运行。
- **决策**：是否需要审批由策略引擎根据主体、工具副作用等级、参数、资源决定；审批是运行的一种等待状态，持久化存储，不占计算资源；可以通过任意渠道处理，全部记录审计。
- **其他方案**：在每个工具或连接器里各自实现确认逻辑。规则分散，无法统一管理和审计。
- **后果**：策略引擎成为关键路径，需要低延迟和高可用；审批的用户体验（清楚说明要做什么）直接影响安全效果。
- **重新评估**：不预期重新评估。

## ADR-011 执行位置按每一步的需求和在线设备动态决定

- **状态**：提议（修订 ADR-004）
- **背景**：ADR-004 假设用户有可执行的本机环境（PC）。实际用户同时使用网页、移动端和 PC 端，且经常跨端：电脑上发起、手机上审批、电脑合上后希望继续。移动端受系统和应用商店限制，不能执行任意代码；网页不能执行本机代码；L3 以移动端用户为主。
- **决策**：
  - 会话和运行始终在云端，所有终端都是视图和执行节点（见 [13 多端客户端](13-multi-device-clients.md)）。
  - 每个客户端向设备注册表上报能力和在线状态。编排服务在调度每个工具调用时决定执行位置：需要某台设备上的数据就在那台设备上；需要执行代码时，PC 在线且策略允许就在 PC 本机，否则在云端执行环境（按 ADR-004 的分级）；移动端只承担系统能力类工具的短时调用。
  - 运行途中设备离线时，运行进入等待并通知用户的其他设备，用户可以选择改到云端继续（需要工作区已同步）。
  - 组织策略可以覆盖规则（例如禁止在个人设备上执行）。
- **其他方案**：
  - 固定在 PC 本机执行（ADR-004 原方案）：移动端和网页用户无法使用执行类能力，跨端接续困难。
  - 全部在云端执行：一致、易管控，但成本高、本地数据需要上传、无法使用用户已登录的网站和本机应用。
- **后果**：需要设备网关、设备注册表、设备端执行协议（签名、续传、幂等）；工作区同步成为跨端接续的前提；执行位置会影响结果（本机环境和云端环境不同），需要在运行记录中标明每一步在哪里执行。
- **重新评估**：如果移动操作系统开放本机代码执行能力，或者大部分用户只使用单一终端。
