# 06 数据与知识

本篇包括三部分：平台自己的数据（运行、消息、制品）怎么存；企业知识（文档、邮件、IM、数据库）怎么接入和检索；记忆怎么管理。

## 一、核心数据模型

```
组织 Org
 ├── 成员 Member（用户、角色、所属部门 / 组）
 ├── 工作空间 Workspace
 │    ├── Agent 定义 AgentDef（版本化：提示词、工具、模型策略、知识范围、审批规则）
 │    ├── 知识源 KnowledgeSource（连接器 + 同步范围 + 同步状态）
 │    └── 触发器 Trigger
 ├── 连接器授权 ConnectorGrant（谁授权了哪个外部账号、范围、有效期）→ 凭证在保险库
 ├── 策略 Policy、配额 Quota
 └── 会话 Session
      └── 运行 Run（状态、预算、用量、发起方式、Agent 定义版本）
           ├── 步骤 Step（类型、输入引用、输出、用量、幂等键、时间）
           ├── 审批 Approval
           ├── 制品 Artifact（元数据；内容在对象存储）
           └── 子运行 Run
记忆 Memory（范围：用户 / 工作空间 / 组织；来源；确认状态；过期时间）
审计事件 AuditEvent（只追加）
用量记录 UsageRecord（按步骤）
```

所有表都带 `org_id`，它是分片键、隔离边界和计费维度。

## 二、存储选型

| 数据 | 特点 | L1 | L2 / L3 |
|---|---|---|---|
| 组织、成员、Agent 定义、策略 | 量小、读多写少、强一致 | 关系库 | 全局控制面库 + 区域只读副本 + 缓存 |
| 会话、运行、步骤元数据 | 写多、按组织和运行查询 | 关系库 | 按 `org_id` 分片的关系库，或分布式关系库 |
| 消息正文、步骤输入输出 | 体积大、写一次读几次、时间越久越少读 | 关系库 JSON 列 | 近期在宽表 / 键值存储，较久的转对象存储 |
| 制品、工作区快照、上传文件 | 大文件 | 对象存储 | 对象存储，分层（热 / 冷 / 归档） |
| 事件流 | 有序、可回放、保留期有限 | 托管消息队列 | Kafka 类，按单元分区 |
| 检索索引 | 全文 + 向量，按组织隔离 | 检索引擎（全文 + 向量一体） | 按组织分片的检索集群；大客户独立索引 |
| 限流计数、会话路由、短期状态 | 高频读写、可丢失 | 缓存 | 区域本地缓存集群 |
| 审计日志 | 只追加、长期保留、不可篡改 | 只追加表 + 定期归档到对象存储（写一次只读） | 专用日志存储，支持导出到客户 SIEM |
| 分析数据 | 用量、质量、成本分析 | 数据仓库 | 数据湖 + 数据仓库 |

### 数据量估算（L2）

- 每天约 150 万日活 × 每人几次运行 × 每次运行几十到几百 KB 的步骤记录 → **每天 TB 级**新增运行数据。
- 工作区快照和制品更大，必须有保留期和分层存储，否则存储成本线性增长。
- 默认保留策略（可按组织配置）：运行明细 90 天 → 之后只保留摘要和审计；工作区快照 7–30 天；审计日志按合规要求（通常 1–7 年）。

## 三、企业知识检索

企业场景（如场景 S3：查合同条款）最核心的要求：**Agent 只能检索到发起人本来就有权看到的内容。**

### 接入管线

```
知识源（网盘、文档库、IM、邮件、工单、代码仓库、数据库）
   │ 连接器：首次全量 + 之后增量（Webhook 或定时拉取变更）
   ▼
解析：PDF、Office、网页、图片（OCR）、表格 → 文本 + 结构 + 元数据
   ▼
切分：按标题、段落、表格切块，保留位置信息（用于引用）
   ▼
权限：读取源系统的 ACL（文档级、文件夹级、群组）→ 映射为平台的主体（用户、组）
   ▼
索引：全文索引 + 向量索引，每个块带上 org_id、知识源、ACL、更新时间
```

nanocode 的 `rag.py` 已经包含切分、BM25、向量、混合排序（RRF）这些核心步骤（第 10 章），平台版本多出来的是：连接器、增量同步、**权限**、规模。

### 权限过滤

| 方案 | 做法 | 取舍 |
|---|---|---|
| **索引时带 ACL，检索时过滤（推荐）** | 每个块存储允许访问的主体列表；检索时用"当前用户 + 所在的组"过滤 | 检索快；需要及时同步 ACL 变更 |
| 检索后实时校验 | 检索出候选后，逐个调用源系统 API 确认用户是否有权限 | 最准确；慢，源系统 API 有限流 |
| 组合 | 索引时过滤 + 对高敏感知识源再做实时校验 | 平衡 |

关键细节：

- **ACL 变更必须优先同步**：人离职、被移出群组、文档权限收紧，这些变更的同步延迟就是泄露窗口。ACL 同步和内容同步分开，ACL 走更快的通道。
- **组成员关系**：从身份系统（SCIM、目录服务）同步，展开嵌套组。
- **无法获取 ACL 的源**：默认只对授权它的那个用户可见，不能对整个组织公开。
- **定时和事件触发的运行**：以触发器创建者的身份检索，而不是以"系统"身份。
- **引用**：答案中的每个结论都带来源链接，用户点击时由源系统再做一次权限检查。

### 检索质量

- 混合检索（全文 + 向量）+ 重排序；按知识源、时间、作者等元数据过滤。
- Agent 可以多轮检索（先检索，读结果，再换关键词检索），这比一次检索更重要。
- 建立按组织的检索评测集（问题 + 应该命中的文档），每次改动检索管线都跑一遍（nanocode 第 10 章的评测方法）。

## 四、记忆

| 层级 | 例子 | 谁能写 | 谁能看 |
|---|---|---|---|
| 用户记忆 | "我习惯用中文回复""我负责华东区" | 用户本人；Agent 提议、用户确认 | 只有本人 |
| 工作空间记忆 | "这个项目用 pytest""报表格式按模板 B" | 工作空间管理员；Agent 提议、管理员确认 | 工作空间成员 |
| 组织记忆 | 公司术语、通用规范 | 组织管理员 | 全组织 |

原则：

- **Agent 提议，人确认**：和 nanocode 的经验候选一样（`/memory accept`），自动提取的记忆不直接生效，避免错误或被注入的内容变成长期规则。
- **记忆可见、可改、可删**：用户能看到 Agent 记住了自己什么，并能删除（也是隐私法规的要求）。
- **有来源和过期时间**：每条记忆记录从哪个运行产生，可以设置过期。
- **检索式加载**：记忆多了以后不是全部放进系统提示词，而是按相关性检索（nanocode 的 `NANOCODE.md` 是全部加载，规模小时可行）。

## 五、数据隔离与驻留

- 逻辑隔离：所有查询必须带 `org_id` 条件，在数据访问层强制，而不是靠每个业务开发者记得加。用自动化测试专门验证跨组织访问一定失败。
- 物理隔离（按需）：大客户独立单元、独立数据库、独立索引、独立加密密钥（客户自管密钥，BYOK）。
- 数据驻留：组织创建时选择区域，用户内容（消息、文件、索引、记忆）只存储在这个区域；跨区域只同步元数据和计费汇总。
- 加密：传输加密；存储加密；高敏感字段（凭证、个人信息）应用层加密。

## 六、制品的托管与分享

Agent 的产出不只是对话里的文字，还有文件、文档、图表、网页、小应用。这些制品需要能保存、查看、分享，部分还要能多人协作。

| 方面 | 设计 |
|---|---|
| 类型 | 文件（代码、表格、PDF）；文档（可在线编辑）；网页和小应用（HTML + 脚本）；图表和数据视图 |
| 版本 | 每次修改生成新版本，可以查看历史、回退；记录是哪个运行、哪个用户产生的 |
| 存储 | 内容在对象存储，元数据在关系库；随组织的数据驻留区域存放 |
| 托管 | 网页和小应用托管在**和平台主站隔离的独立域名**下，每个制品一个独立来源；严格的内容安全策略；拿不到平台的登录态和令牌 |
| 分享权限 | 私有 → 指定成员 → 工作空间 → 组织 → 持有链接的人 → 公开；组织策略决定最大可分享范围（例如企业禁止公开分享） |
| 协作 | 评论、多人编辑；需要实时数据或共享状态的小应用，通过平台提供的受控接口读写，权限显式声明并经用户批准，不能直接访问用户的连接器和数据 |
| 再次交给 Agent | 用户可以让 Agent 基于已有制品继续修改；读取别人分享的制品时，内容视为不可信（可能含提示词注入） |
| 保留与删除 | 按组织策略设定保留期；删除会话时可选择是否保留制品 |
| 滥用 | 公开分享的网页可能被用来做钓鱼或传播违法内容：发布前做内容扫描，提供举报入口，可以一键下线 |
| 导出 | 下载为常见格式；文档可导出到外部文档系统（通过连接器） |
