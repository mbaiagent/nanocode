# 05 模型层

模型层由**模型网关**（所有模型调用的唯一出口）和 L2 起自建的**推理集群**组成。

本篇讲模型层的工程设计。模型本身为什么会这样表现（训练怎样塑造 Agent 能力、长上下文为什么容易出错、常见失败的模型层原因），见学习章节 [13 模型视角](../13-model-perspective.md)。

在 L2、L3，模型推理很可能是最大的成本项，也是最容易被外部因素（厂商限流、故障、涨价、停服）影响的环节。模型层的目标是：**稳定、可控成本、可快速切换**。

## 一、模型网关

### 职责

| 职责 | 说明 |
|---|---|
| 统一接口 | 对内只有一种消息格式（nanocode `messages.py` 的统一格式就是这个思路），网关负责翻译成各厂商协议，包括厂商特有字段的原样回传（如 Gemini 的 `thought_signature`，nanocode issue #17） |
| 凭证管理 | 厂商 API Key 只存在网关；调用方用短期的内部令牌，绑定组织、运行和预算 |
| 路由 | 按任务类型、难度、成本、延迟、区域、合规要求选择模型和厂商 |
| 限流与配额 | 按组织、用户、Agent 定义、运行限流和扣减预算 |
| 排队与退避 | 厂商限流时统一排队，避免所有调用方同时重试（nanocode 每个进程各自重试，规模大了会互相加剧） |
| 故障切换 | 厂商故障或超时时切换到备用模型，切换规则按 Agent 定义配置（有些任务换模型会显著影响质量，宁可等待） |
| 缓存 | 提示词缓存（厂商侧）、相同请求的结果缓存（仅限确定性场景） |
| 内容安全 | 输入、输出的安全检查（按区域法规和组织策略） |
| 计量 | 每次调用的输入、输出、缓存命中 token，模型版本，延迟，写入计量 |
| 审计 | 按组织策略保存请求和响应（或只保存摘要），用于审计和排查 |

### 路由策略

```
请求（Agent 定义、步骤类型、上下文长度、组织策略、区域）
   │
   ├── 合规过滤：只保留这个组织、这个区域允许的模型
   ├── 能力过滤：上下文窗口够不够、是否支持工具调用 / 图片 / 长输出
   ├── 选择档位：
   │     大模型：规划、复杂推理、写代码、最终答复
   │     中模型：一般工具调用、总结
   │     小模型：分类、提取、改写、路由判断、上下文压缩
   └── 选择具体厂商和部署：按健康状况、剩余配额、延迟、价格加权
```

"步骤类型"由运行时标注：同一个运行里，规划步骤用大模型，执行中的简单步骤用小模型，可以显著降低成本。效果必须由评测数据证明（见 09），不能凭感觉降级。

### 限流设计

- 令牌桶按多个维度同时生效：组织（每分钟 token、每分钟请求）、用户、运行、厂商账号。
- 计数放在缓存集群里；L2 起按区域本地计数、定期全局对齐，避免全局热点。
- 厂商返回的配额耗尽（nanocode 的 `QuotaExhausted`：配额类 429 不重试）和普通限流区别处理：前者切换账号或厂商，后者排队退避。
- 排队有上限和超时，超时后返回明确的"繁忙，请稍后"，而不是无限等待。

## 二、成本模型

### 估算公式

```
每次运行的模型成本 ≈ Σ(每一步) [ 未缓存输入 × 输入单价 + 缓存命中输入 × 缓存单价 + 输出 × 输出单价 ]
每日模型成本 ≈ 日运行次数 × 平均每次运行成本
```

Agent 的特点是**输入远大于输出**：每一步都要带上之前的上下文。所以提示词缓存命中率和上下文长度控制，对成本的影响比模型单价更大。

### L2 的量级

按 [01 愿景与范围](01-vision-and-scope.md) 的假设：高峰约每秒 1.5 亿输入 token。如果全部按便宜模型、每百万输入 token 约 1 美元、不做任何优化，高峰时每天的成本是千万美元量级。这说明：

- 不做路由、缓存、上下文控制，L2 的商业模式不成立；
- 定价必须和用量挂钩（订阅 + 用量上限，或按量计费），见 [10 交付形态与商业化](10-delivery-and-business.md)；
- 自建推理集群承担大部分简单步骤，是 L2 的必选项，不是优化项。

### 降本手段（按收益排序）

1. **提示词缓存**：系统提示词、工具定义、早期对话保持稳定并放在前面。缓存命中的输入通常比未命中便宜一个数量级。
2. **上下文控制**：工具结果截断、及时压缩、子 Agent 隔离大段探索（只把摘要带回主上下文）。
3. **模型分级路由**：简单步骤用小模型。
4. **快速路径**：简单请求不走完整的 Agent 循环（见 03）。
5. **自建推理**：对高频的中小模型调用，自建推理的单位成本可以低于 API 价格，但需要足够的稳定用量来摊薄 GPU 成本。
6. **批处理**：不着急的任务（夜间报表、批量处理）用厂商的批处理接口或闲时算力，通常有明显折扣。

## 三、推理集群（L2 起）

| 方面 | 设计 |
|---|---|
| 模型 | 开源模型（经过评测筛选，必要时针对平台的工具调用格式微调）；L3 起以自研为主 |
| 部署 | 高性能推理引擎，连续批处理，KV 缓存跨请求复用（对 Agent 这种前缀高度重复的负载收益很大） |
| 调度 | 按模型和上下文长度分池；按负载自动扩缩；同一会话的请求尽量路由到同一副本以复用 KV 缓存 |
| 容量 | 按高峰小模型调用量规划，外部厂商承担溢出和大模型调用 |
| 质量 | 新模型或新版本上线必须通过评测门禁，灰度放量，可一键回退 |

## 四、L3：模型和算力本身成为核心

到十亿用户，问题的性质变了：

- **外部采购无法满足**：每秒百亿级 token 超过任何一家模型厂商能卖给单个客户的量。
- **必须自研或深度定制模型**：针对 Agent 工作负载（长上下文、工具调用、规划）优化，模型的效率直接决定毛利。
- **算力和电力是战略资源**：自建数据中心、长期芯片采购、GW 级电力规划，需要以年为单位提前布局。
- **推理在终端和边缘分担**：小模型在手机、电脑上运行，处理简单请求和隐私敏感的请求，云端只处理需要大模型的部分。

这已经是公司战略层面的决定，见 ADR-007。

## 五、接口（内部）

```
POST /internal/v1/complete
{
  "run_id": "...", "step": 12,
  "purpose": "plan | tool_use | summarize | classify | final_answer",   // 用于路由
  "requirements": { "tools": true, "vision": false, "min_context": 64000 },
  "messages": [ ... 统一格式 ... ],
  "tools": [ ... ],
  "budget": { "max_output_tokens": 4096, "max_cost": 0.5 },
  "stream": true
}
→ 流式返回：文字片段、工具调用、用量、实际使用的模型和厂商
```

调用方拿到的响应里总是包含"实际使用的模型"，运行时据此写入系统提示词的运行时身份和审计记录。
