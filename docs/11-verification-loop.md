# 11 · 验证循环：检查、纠正、终审

> 对应源码：`nanocode/verify.py`、`subcheck.py`、`risk.py`、`review.py`、`lessons.py`，以及 `agent.py` 里的 `_verify` / `_run_subagent` / `_finish_review`、`permissions.py` 里的 `review` 模式

第 01 章说过：Agent 就是一个 while 循环，模型不再调用工具就结束。这个循环有一个弱点——**"结束"是模型自己宣布的**。模型说"改好了"，不等于改对了。

## 循环真正的关键：一个会让工作失败的检查

把 Agent 的工作想成一个闭环：

```
产出 ──▶ 检查 ──▶ 通过？──是──▶ 结束
          ▲         │否
          └─ 纠正 ◀─┘   （带上检查的输出，限次数）
```

这里的关键不是"循环"，而是**检查**：它必须是一个**模型说了不算、能够真的判失败**的东西——测试、类型检查、lint。没有这样的检查，循环只是让模型多说几遍"我觉得没问题"。

围绕这个闭环，nanocode 做了四件事，对应本章四节：

| 要解决的问题 | 机制 | 源码 |
|---|---|---|
| 改完代码没人检查 | 自动验证：想结束时先跑检查命令，不过就回头修 | `verify.py` |
| 子 Agent 说"搞定了"，主 Agent 只能信 | 子 Agent 验收：系统核对改了什么、有没有越界、检查过没过 | `subcheck.py` |
| 逐条确认让人疲劳，反而削弱真正危险操作的确认 | 终审模式：无害步骤自动放行，高风险永远确认，结束时汇总 diff | `risk.py`、`review.py` |
| 同样的坑每次会话都再踩一遍 | 经验沉淀：被打回又修好的回合生成候选约束，你确认后才写入记忆 | `lessons.py` |

最后一节讲怎么**衡量**这些机制到底有没有用（评测任务 T11–T13）。

## 1. 自动验证

### 用法

```bash
nanocode --verify "pytest -q"
```

或写进 `.nanocode/settings.json`：

```json
{"verify": {"command": "pytest -q", "max_retries": 3, "timeout": 300}}
```

也可以只写字符串：`"verify": "pytest -q"`。`max_retries` 默认 3，`timeout` 默认 300 秒。

### 发生了什么

在 `agent.py` 的主循环里，模型不再调用工具时，原来是直接结束。现在多了一道关：

```
模型这一步没有工具调用
   │
   ├─ 配了 verify 且本轮改动过东西？ ──否──▶ （走 Stop hook）结束
   │是
   ├─ 运行检查命令
   │    ├─ 通过 ──▶ 结束
   │    └─ 失败 ──▶ 把输出末尾 4000 字符包进 <verify-feedback> 追加给模型，continue
   │
   └─ 停止条件：重试超过 max_retries，或同一个错误连续出现两次（没有进展）
        ──▶ 结束，把最后一次失败输出附在回答后面交给你
```

几个值得细看的设计：

- **"改动过东西"怎么判断**：本轮有任何成功执行的**非只读**工具（写文件、bash 等）就算，包括子 Agent 的改动。纯问答、只读调查不会触发检查，免得浪费时间。这个判断偏保守——只跑 `ls` 的 bash 也算——宁可多检查，不漏。
- **为什么要有"同一个错误两次就停"**：模型有时会"假装修了"，重试几次输出一模一样。这时再重试只是烧钱。判断"一样"时会去掉耗时（`0.012s` 和 `0.340s` 不算不同），见 `verify.signature()`。
- **为什么保留输出的末尾而不是开头**：测试框架的报错总结几乎都在最后（`truncate()` 保留头尾，这里只留尾）。
- **超时会连子进程一起杀**（`start_new_session` + `killpg`），否则 `pytest` 起的子进程会留在后台。
- **和 `Stop` hook 的区别**：`Stop` hook 要你自己写脚本、没有次数上限、不看有没有改动过东西（第 04 章）；`verify` 是现成的、有上限、有进展判断。先 `verify` 通过，再轮到 `Stop` hook。两者可以同时用。

### 怎么看到它

- 事件：`verify`（`status` 是 `running` / `pass` / `fail`，带 `attempt`、`command`、`exit_code`、`output`）。CLI 和 Web 面板都会显示。
- 单次模式（`-p`）验证失败时**退出码为 1**，脚本和 CI 能直接判断：

  ```bash
  nanocode -p "修复登录 bug" --verify "pytest -q" || echo "没修好"
  ```

### 它不能做什么

- **检查本身要可靠**。测试写得弱，通过也不代表对（见第 6 节的 T12、T13）。
- 只对主 Agent 生效；子 Agent 靠第 2 节的验收。
- 检查命令来自项目的 `settings.json` 时，和 hooks 一样需要先信任这个项目（第 04 章）；`--verify` 是你自己在命令行给的，直接生效。

## 2. 子 Agent 验收

第 06 章讲过，子 Agent 的价值是隔离上下文，主 Agent 只看到它的结论。但"只看到结论"也是风险：结论可能没有依据，子 Agent 还可能悄悄改了不该碰的文件。

### 系统生成的验收报告

不管有没有带任何条件，子 Agent 返回的结论后面都会附上这样一段（**由系统核对生成，不是子 Agent 自述**）：

```
（子 Agent 的结论）

---
[验收报告：由系统核对生成，不是子 Agent 自述]
- 改动文件：src/parser.py, tests/test_parser.py
- 范围：均在允许范围内
- 检查：`pytest -q tests/test_parser.py` 通过（第 2 次）
```

没配检查时，最后一行是"检查：未配置，以上结论**未经验证**"。主 Agent 靠这一行区分"核对过的事实"和"子 Agent 的一面之词"。

### 两个可选条件

`task` 工具有两个可选参数（见 `tools/planning.py`）：

- `check`：一条检查命令。子 Agent 汇报后由系统运行，不通过就把输出交还给它接着修（它保留自己的上下文），**最多重做 2 次**，用完仍不过，报告里写"未通过，子 Agent 的结论不可信"。这条命令是模型传进来的，所以**和 `bash` 一样要过权限**——没放行就不执行，报告里写"未验证"。
- `allowed_paths`：允许修改的路径，如 `["src/parser/", "tests/test_parser.py"]`，支持目录前缀和 `*`；空列表表示只读任务。

### 两道防线：事前拒绝 + 事后发现

| 子 Agent 的做法 | 怎么处理 |
|---|---|
| 用 `write_file` / `edit_file` 改范围外的文件 | **事前拒绝**：工具直接返回"不在允许修改的范围内" |
| 用 `bash`（`sed -i`、重定向……）改范围外的文件 | **事后发现**：前后各拍一次文件快照对比，发现越界就让它还原 |

bash 没法事前管，因为命令可以千变万化。所以越界检测对 bash 是"发现"而不是"阻止"——要强隔离只能靠容器或沙箱。

快照比较的是**内容摘要**，不是修改时间。早期版本只比大小和时间，结果子 Agent 按要求把文件还原后仍被判成改动，重做流程永远走不通——这是测试抓到的真实问题。现在"改了又还原"、"只 touch 一下"都不算改动（超过 1MB 的文件退回只比大小和时间；文件数超过 2 万个时放弃统计，报告里明说，不假装检查过）。

## 3. 终审模式

### 问题：事事确认 vs 全部放行

`default` 模式下一个很小的任务（读文件、改文件、跑测试、看 `git status`）要点 4 次确认，其中大半是明显无害的。人会习惯性地点"允许"，真正危险的那一次也跟着点掉了。想少点几次，唯一的办法是在 allow 里写 `bash(*)`——但这样 `rm -rf build` 也零确认了。只有两个极端，没有中间档。

### 三层

```bash
nanocode --mode review        # 或交互里 /mode review
```

| 层 | 内容 | 怎么处理 |
|---|---|---|
| 自动放行 | 读项目内文件；改项目内文件；白名单内的检查命令（`pytest`、`python -m unittest`、`mypy`、`ruff check`、`cargo test`、`go test`、`npm test`、`make test`，只读的 `git status/diff/log/show`、`ls/cat/grep` 等） | 不打断 |
| 询问 | 其余所有东西：`git commit`、`mv`、运行任意脚本…… | 和 default 一样问你 |
| **永远确认** | 删除（`rm`）、`git push / reset --hard / clean`、提权、改权限、结束进程、安装依赖、`curl \| sh`；写项目外的路径、写 `.env` / `.git/` / `.nanocode/` / 密钥文件 | **无论 allow 规则怎么写都要问**，也不支持「总是允许」 |

用第 04 章的决策流程看，`review` 模式比其他模式多了两处（`permissions.py` 的 `check()`）：deny 之后、allow 之前插入"高风险一律确认"；allow 规则之后再加"项目内编辑 / 白名单命令自动放行"。

### 失败安全：宁可多问，不可放过

分类器（`risk.py`）的方向很重要：**白名单**决定什么可以自动放行，而不是黑名单决定什么要拦。

- 自动放行的命令里**不能出现任何 shell 拼接符**（`; & | ` $ < > ( ) { }`）、不能引用项目外路径或敏感文件。`pytest -q 2>&1 | tail -1` 因为有管道，会被问。
- **认不出的一律问**。把命令藏进 `python -c "..."` 只会落到"询问"，不会被放行。
- 高风险模式单独识别，且**优先于 allow 规则**。用户点「总是允许」对高风险只放行这一次，不留规则。

这是启发式规则，不是沙箱。已知局限一定要知道：**测试命令会执行项目里的代码，包括 Agent 刚写的**。如果它写了个会删文件的测试再跑 `pytest`，会被自动放行。终审汇总是事后给你看的，不是事前拦截。需要强隔离请用容器或虚拟机。

### 终审汇总

任务结束时，如果本轮改过文件，会汇总改动（`review.py`）。这是用 Mock 模型跑 `nanocode --provider mock --mode review -p "创建文件 hello.py"` 的真实输出（节选）：

```
═ 终审：本轮改动 1 个文件 · 自动验证：未配置或未运行
  新增  nanocode_demo/hello_091349_49b6.py (+7 -0)
    --- a/nanocode_demo/hello_091349_49b6.py
    +++ b/nanocode_demo/hello_091349_49b6.py
    @@ -0,0 +1,7 @@
    +"""由 nanocode 的 Mock 模型生成的演示文件。"""
    ...
  提交、推送等最后一步仍需你确认。
```

注意这次运行里：写文件**自动放行**了；而 Mock 想运行刚生成的 `python3 nanocode_demo/hello_....py`，不在白名单里，所以被拦下要确认（单次模式没人可问，被拒绝）。

diff 怎么来的：写文件工具动手**之前**先记下原文，结束时拿现在的内容比（`review.remember()`）。bash 造成的改动没有原文，只列文件名并标明"经 bash 改动，无 diff"；超过 200KB 或不是文本的文件同样只列文件名；单个 diff 截断在 6000 字符，最多列 30 个文件；子 Agent 的改动也包含在内。

它是**汇总，不是回滚**——看完觉得不对，需要你自己用 git 还原。提交、推送本来就不在白名单里，所以最后一步仍然是你点头。

## 4. 经验沉淀

### 问题

同样的错误（比如总忘了某条检查必须通过）会在不同会话里反复出现，每次都要人来纠正。

### 三条规矩（`lessons.py`）

1. **只记有证据的**。候选来自失败检查输出的**原文**和打回之后实际改动的文件，用固定模板生成，**不调用模型、不让模型总结**——模型的主观总结可能是错的，写进记忆就会影响以后每一次会话。
2. **先展示，再写入**。候选只是提示，你确认后才写。避免把一次性的失误固化成规则。
3. **只在"被打回过、后来确实通过了"时产生**。验证放弃的回合没有可靠结论，不沉淀。这也是它依赖第 1 节的原因：没有可靠的检查，就没法判断哪些结果是"被接受的"。

### 用法

回合结束时可能出现：

```
💡 经验候选 #1（来自被自动验证打回又修好的回合，确认后才会写入项目记忆）
    改动后需通过 `pytest -q`（曾因 「FAILED tests/test_slugs.py::test_slug - AssertionError…」 被打回，修复涉及 src/slugs.py）
    写入：/memory accept 1　丢弃：/memory reject 1
```

- `/memory`：查看已加载的记忆，以及待确认的候选
- `/memory accept [编号|all]`：写入项目的 `NANOCODE.md`（下次启动自动加载进系统提示词）
- `/memory reject [编号|all]`：丢弃，本会话不再提示同样的约束

同一条约束（同一检查命令）已经在待确认列表、被拒绝过、或记忆里已经有，就不会再提示。`settings.json` 里 `"suggest_memory": false` 可以关闭。

证据来自命令输出，里面什么都可能有，所以写入前会压成单行、去掉控制字符和反引号、限长，防止输出里的内容变成注入记忆文件的指令。

### 局限

它只能从"检查命令挂了"里学到东西，学不到"某个目录不能改"这种来自你纠正的经验——那类请直接用 `# 一句话` 追加。未确认的候选只存在于当前会话；`-p` 单次模式下只能看到提示，没法确认。

## 5. 事件一览

| 事件 | 什么时候发 | 谁订阅 |
|---|---|---|
| `verify` | 每次自动验证（`running` → `pass` / `fail`） | CLI、Web |
| `subagent_end` | 子 Agent 结束，带 `report`（验收报告的结构化版本） | CLI；Web 调试面板的事件流 |
| `review` | 终审模式下，回合结束且有改动 | CLI、Web |
| `lesson` | 被打回又修好的回合（带证据） | `Session` 据此生成 `memory_pending` |
| `memory_pending` | 有新的待确认候选 | CLI、Web |

## 6. 怎么衡量这些机制有没有用

不能凭感觉说"加了验证更好"。`evals/agent_tasks/` 里新增了三个专门设了陷阱的任务（T11–T13）：**最容易写出的第一次尝试是错的**。分两类，测的东西不同：

| 类型 | 任务 | 第一次尝试能通过 Agent 看得到的测试吗 | 测什么 |
|---|---|---|---|
| `caught_by_visible` | T11 改函数签名（调用点有别名导入、`functools.partial`） | 不能，跑一遍就红 | 会不会跑检查并据此改正；`--verify` 能直接帮上忙 |
| `needs_own_checks` | T12 规格里的约束；T13 修 bug 别弄坏旧行为 | 能，可见测试全绿 | 会不会读规格、自己补用例；观察验证循环**有没有带来假自信** |

第二类很重要：如果检查本身看不出问题，"检查绿了就收手"反而让人更放心地接受错误结果。

"确实有陷阱"是被测试保证的，不是口头声明：每个任务带一份 `naive/`（典型的第一次尝试），`tests/test_agent_eval.py` 断言它过不了判定。另外有一个用**脚本化模型**的端到端演示：同一份剧本（先写第一次尝试、收到失败反馈再改对），不开 `--verify` 时 T11 判定失败，开了就通过；T12、T13 开了也一样失败。**这只证明评测有区分度，不是真实模型的结果**——真实数据要用真实模型去跑：

```bash
python3 evals/agent_tasks/run.py --provider deepseek --model deepseek-chat --tasks T11,T12,T13 --repeat 5
```

## 配置速查

| 配置 | 位置 | 说明 |
|---|---|---|
| `verify` | `settings.json`（项目里的需先信任）/ `--verify` | 检查命令；`max_retries`（默认 3）、`timeout`（默认 300 秒） |
| `--mode review` | 命令行 / `settings.json` 的 `mode` / `/mode review` | 终审模式 |
| `task` 的 `check`、`allowed_paths` | 模型调用 `task` 时传 | 子 Agent 验收条件 |
| `suggest_memory` | `settings.json` | 设为 `false` 关闭经验候选 |

## 思考题

1. 自动验证里，"同一个错误连续出现两次就停"和"最多重试 3 次"为什么要同时存在？只留一个会怎样？
2. 为什么终审模式用**白名单**自动放行，而不是用黑名单拦截危险命令？把 `python -c "import shutil; shutil.rmtree('x')"` 分别放进两种方案里，会发生什么？
3. 子 Agent 越界检测对 `write_file` 是事前拒绝、对 `bash` 是事后发现。能不能让 `bash` 也事前拒绝？需要付出什么代价？
4. T12 的第一次尝试能通过可见测试。开了 `--verify "pytest -q"` 后它仍然失败——这说明了验证循环的什么局限？你会怎么改进检查命令？
5. 经验候选为什么不让模型来总结？这样做的代价是什么？
