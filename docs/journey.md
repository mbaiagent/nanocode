# 开发历程：怎么做出来的、踩过哪些坑

这篇记录 nanocode 从第一行代码到多用户平台的过程：每个阶段做了什么，遇到了什么问题，原因是什么，怎么解决，又怎么保证不再犯。
每个问题都能在 git 历史里找到对应的提交（括号里的 `#数字` 是 GitHub issue）。

## 怎么协作的

这个项目由作者提需求、定方向、审查和决定合并；编码、测试、真实环境验证和文档由 AI 编程助手（Claude Code）在作者的指示下完成。
过程中有几条一直坚持的规矩：

- **每个改动开一个分支**，测试全部通过、作者同意后才合进主干。
- **先复现再修**：修 bug 时先写一个在旧代码上会失败的测试，修好后它通过，以后也不会再犯。
- **真实环境验证**：单元测试之外，用真实模型、真实浏览器、真实 Docker / PostgreSQL / Redis 跑一遍，结果记在 [verification/](../verification/) 里。
- **文档和代码不许脱节**：有一个专门的测试检查命令行参数、配置项、环境变量、斜杠命令、代码行数、测试数量这些写在文档里的东西和代码是否一致。
- **不夸大**：数字都要能在仓库里核实；没做到的（比如没在真实的千人生产环境跑过）明确写出来。

## 遇到的问题和解决办法

### 安全

**1. 权限检查能被 `~` 和软链接绕过**
- 现象：`accept_edits` 模式只允许改项目内的文件，但写 `~/.bashrc` 或者经过项目里的软链接写到外面，都能通过。
- 原因：权限检查和工具各自解析路径，权限检查看到的是字面上的路径，工具实际写的是展开后的路径。
- 解决：两边共用同一个 `resolve_path`（展开 `~`、取真实路径），规则同时匹配规范化后的路径。
- 教训：**做检查的和做事的必须看同一个东西**，否则中间的差异就是漏洞。

**2. 别的网站能操控本机的 Web 面板**
- 现象：任意网页用 `text/plain` 的跨站 POST 就能给本机的 nanocode 发指令；DNS 重绑定也能绕过同源限制。
- 解决：校验 Host 和 Origin；POST 只收 JSON；所有 `/api` 请求都要带启动时随机生成的令牌。后来又把事件流改成用一次性票据（令牌不再出现在 URL 里），请求体加 1MB 上限（#3 #6）。

**3. 打开一个陌生仓库就可能被攻击**
- 现象：项目里的 `.nanocode/settings.json` 能配 hooks、MCP 服务器（都会执行命令）、`bypass` 模式、把请求发到别的地址。clone 一个恶意仓库再启动 nanocode，就等于执行了对方的命令。
- 解决：工作区信任（`trust.py`）。项目配置里的敏感项第一次出现时要用户确认，记下"目录 + 配置指纹"，配置一变就重新询问。

**4. bash 的 allow / deny 规则对复合命令失效（#16）**
- 现象：模型习惯加 `cd dir &&` 前缀，导致 allow 规则不命中；反过来 `python3 -m unittest && rm -rf /` 能被 `bash(python3 -m unittest*)` 放行，`bash(rm -rf*)` 也拦不住 `cd x && rm -rf y`。
- 原因：对整条命令做通配符匹配。
- 解决：按 `&&` `||` `;` `|` 和换行拆段（引号里的不拆）；allow 要每一段都命中，deny 任一段命中就拒绝；`$(…)` 和反引号里的命令，allow 不放行、deny 会展开去查。

### Web 界面

**5. 关掉页面后 Agent 卡死十分钟（#13）**
- 现象：权限询问期间关掉浏览器，Agent 一直占着"忙碌"锁，等满 10 分钟超时才释放。
- 解决：没有浏览器连着超过 30 秒就按拒绝处理；刷新页面会很快重连，不受影响。

**6. 长任务后刷新页面，界面显示"空闲"其实还在跑（#4）**
- 原因：事件历史最多保留 2000 条，长任务开头的事件被挤掉了，光靠重放事件判断不出状态。
- 解决：页面加载时以服务端的 `busy` 为准；之后的刷新不覆盖，避免 `turn_end` 刚发出、服务端还没清状态时卡在"忙碌"。

**7. iOS 内嵌浏览器里调试面板按钮失灵**
- 原因：变量名 `main` 可能和内嵌浏览器注入的脚本重名，`const` 重复声明直接报错。
- 解决：改名 `mainEl`。小问题，但只有在真机上点过才会发现。

### 模型协议兼容

**8. 配额用完后不停重试（#1）**
- 现象：429 一律退避重试，配额耗尽时白等，用户也不知道什么时候能恢复。
- 解决：从响应头（`Retry-After`、`X-RateLimit-Reset` 的三种格式）和响应文本判断是瞬时限流还是配额用完；配额用完就不重试，换算成本地时间告诉用户。

**9. Gemini thinking 模型第二轮报 400（#17）**
- 原因：Gemini 在工具调用里返回了 `extra_content.google.thought_signature`，流式解析只保留了 id / name / arguments，下一轮历史里没有它，服务端拒收。
- 解决：把这个字段原样存在 tool_use 块里，下一轮带回去；发给 Anthropic 协议时不发它不认识的字段。用真实的 Gemini 多轮对话验证过。

**10. 经 OpenRouter 用 Anthropic 协议时流末尾崩溃（#20）**
- 原因：OpenRouter 在 `message_stop` 之后又追加了 `data: [DONE]`（这是 OpenAI 协议的习惯），解析器对每行都 `json.loads`。
- 解决：跳过 `[DONE]` 和无法解析的事件。教训：**兼容协议的实现永远不会完全一致，解析要宽容**。

**11. Anthropic 协议 usage 是显式的 `null` 时崩溃（#18）**
- 解决：`null` 和缺失同样处理。

**12. 问 Agent"你是什么模型"，它乱答（#21）**
- 现象：真实的 Gemini 回答过"Mock"、"Claude 3.5 Sonnet"。
- 原因：模型只能看到系统提示词和对话，里面没有这个信息，它就从训练数据或项目文档里猜。
- 解决：把当前的 provider / model / protocol 写进系统提示词的环境段。这件事也是[第 13 章](13-model-perspective.md)"模型只知道你给它看的东西"的一个实例。

### 可靠性

**13. 会话文件写到一半崩溃就全丢（#8）**
- 解决：先写临时文件、`fsync`，再 `os.replace` 原子替换；读到损坏的文件就改名备份，再试更早的会话，而不是直接抛异常。
- 后来为多用户部署又加了"每一步调用模型前都保存"：沙箱随时可能被回收，最多丢一步。

### 评测

**14. 配额用完被记成"模型 0 分"**
- 现象：一次 Gemini 评测得到 0/13，看起来像模型很差，其实是 API 一直返回 429。
- 解决：模型接口出错中止的运行单独标记，不计入通过率，报告里单独提示；连续出错就提前停止。
- 教训：**评测要区分"模型做不好"和"根本没让模型做"**，否则数字没有意义。修好后用 DeepSeek 跑出 37/39，两次失败都是 T10（写测试没发现第 4 个注入的 bug），属于模型能力问题。

### 多用户平台

**15. 网关转发流式响应时内容错乱**
- 原因：为了逐行转发，直接读了 `resp.fp`，绕过了 HTTP 库对分块编码（chunked）的解码，把分块长度当成内容转发出去了。
- 解决：改用 `resp.readline()`，加了回归测试。这个问题只在接真实上游时出现（假服务器没用分块编码），所以**真实链路必须跑一遍**。

**16. Docker 沙箱既要断网又要能被访问**
- 现象：沙箱放在 Docker 的 internal 网络里就出不了外网，但 internal 网络也不能把端口映射到宿主机，控制面访问不到沙箱。
- 解决：不映射端口，控制面直接访问容器在沙箱网络里的 IP；沙箱访问网关走网桥地址。实测沙箱访问外网和云元数据地址都失败、访问网关成功。

**17. 明确配置的网关地址被忽略**
- 原因：启动器"建议"的地址（Docker 网桥）优先级比用户显式配置的 `NCS_GATEWAY_URL` 还高，网关单独部署时沙箱连错地方。
- 解决：显式配置优先，其次启动器建议，最后默认值；加了测试。

**18. 构建沙箱镜像时 pip 连不上代理**
- 解决：沙箱镜像根本不需要 pip 安装——nanocode 零依赖，直接复制源码、设 `PYTHONPATH`。零依赖在这里又省了一次事。

**19. 测试里的小坑**
- 测试客户端检查 `Set-Cookie`，服务器发的是小写 `set-cookie`：HTTP 头不区分大小写，客户端统一转小写。
- 隔离检查把别的测试的模型调用也算进来了：加 `since` 参数只看本次的。

**20. 多个控制面副本可能重复启动同一个沙箱**
- 解决：在数据库里原子地"抢占启动"（一条带条件的 UPDATE），抢到的副本才去启动。

### 扩展可见性

**21. 装了 MCP 服务器却看不到装了什么、为什么没连上**
- 原因：连接失败只打一行日志；服务器的 stderr 被直接丢弃，缺依赖之类的原因根本看不到。
- 解决：每个服务器记录连接结果，stderr 保留最后 20 行；新增 `/mcp`、`/skills` 命令和 Web 的「扩展」面板；平台管理员可以通过 `NCS_SANDBOX_MCP_SERVERS` 给沙箱配服务器。
- 用官方的 filesystem、memory、fetch 服务器和真实模型实测：技能加载 → 抓网页 → 写进知识图谱整条链路可用。

**22. 截图时顺手发现的 bug**
- 会话下拉框里的标题显示成 `[{'type': 'text', ...`：用户消息是内容块列表时，代码直接 `str()` 了整个列表。改成取文字块，加了测试。

## 几条体会

1. **Agent 的核心很小，难的是周边。** 循环几十行就写完了，真正花时间的是权限、信任、上下文、协议兼容和评测。
2. **单元测试证明"我以为的行为"，真实环境证明"实际的行为"。** 分块编码、`[DONE]`、`thought_signature`、Docker 网络，这些都是测试全绿之后在真实环境里才暴露的。
3. **安全问题大多出在"两个地方对同一件事的理解不一致"**：权限检查和工具对路径的理解、规则和 shell 对命令的理解、配置作者和使用者的身份。
4. **数字要经得起追问。** 评测分清基础设施错误，文档数字有测试守着，简历里只写能核实的东西。
5. **零依赖是一种约束，也是一种自由。** 写起来多花些力气（自己写 HTTP 路由、SSE、JSON-RPC），但部署、打包、沙箱镜像都简单得多。
